# 4 天、36 次提交、1.86 万行 C#：一个人和一个 AI Agent 能做出什么

> 记录 2026.10.19 – 10.22 开发「游戏优化助手」的全过程。
> 不含"AI 改变世界"的感慨，只写我怎么分工、翻过哪些车、哪些地方 AI 靠不住。

---

## 一、结果先摆出来

| 项 | 数字 |
|---|---|
| 时间 | 4 天（10.19 晚 – 10.22 晚） |
| 提交 | 36 次 |
| 代码量 | src + tests 共 18,656 行 C#（.NET 8 + WPF/MVVM） |
| 测试 | 574 个 xUnit 用例，全绿 |
| 版本 | v0.1 → v2.2.2，共 10 个发布版本 |
| 形态 | Windows 桌面应用，单文件 exe，系统托盘常驻 |

做的是一个「显存不足 / 卡顿掉帧」的诊断工具。它不喊"一键提速"，只做一件事：把**显存水位、内存、GPU 占用、CPU 分核峰值、外设电量**摆到同一屏，告诉你卡顿到底来自哪里。

先说结论：**AI Agent 让我一个人做到了原本需要一个小组才敢接的活，但它没有替我做过任何一个判断。**

---

## 二、我是怎么分工的

这是全文最重要的一节。我的分工不是"我提需求、AI 写代码"这么含糊，而是按**责任**切的：

| 我负责 | AI 负责 |
|---|---|
| 需求边界：做什么、明确不做什么 | 按约定写实现 |
| 技术选型：.NET 8 + WPF、为什么不用 Electron | 补齐我没想到的边界条件 |
| 判定口径：什么情况算"显存紧张" | 把口径翻译成代码和测试 |
| 验收：每条需求我自己点一遍 | 写测试，但**测什么由我定** |
| 决策是否发布、是否回滚 | 跑构建、跑测试、报错定位 |

有一条边界我守得很死：**"能不能做"由 AI 回答，"要不要做"必须我回答。**

第一天就让 AI 写了 `AGENTS.md`，把项目约定固化下来——目录纪律、命名、什么能进 Core 什么必须留 App、失败必须上报不许静默。这份文件后来救了我很多次：AI 每次新开会话都会先读它，减少"越写越飘"。

## 三、三天里实际发生了什么

**10.19（第一天，6 小时）**：MVP 立起来。显存采集、Steam 库扫描、游戏模式、实时曲线，v0.1 能在自己机器上跑了。当天就踩了 5 个坑：
- PowerShell 脚本编码导致 ParserError；
- WeGame 的 DeltaForce 显示成英文，得手动做中文名映射；
- 游戏进程检测识别不到游戏进程；
- PresentMon 写 CSV 被独占，轮询读不到 → 改成读 stdout 流；
- 采集失败时界面还在显示数字 → 加"失败不许谎报成功"。

**10.20（第二天）**：从"能跑"到"敢用"。加托盘常驻、外设页、CPU 详情页，中间有一次重构和一次功能撤回（见第四节）。

**10.21（第三天）**：单日 5 个版本。修了两个硬件相关的怪 bug，加了完整的下载器（多线程分片、断点续传、SHA1 校验、坏片定位重下），测试从 457 涨到 561。

**10.22（第四天）**：修最后一个 bug，做完文件归位，测试到 574，收工。

## 四、一个反例：做出来又撤回的悬浮窗

10.20 晚上 22:21，我提交了「游戏内悬浮窗」。**3 分钟后撤回，第 4 分钟写文档记录为什么撤回。**

原因不是做不出来——实机验证过，五项指标正常显示，拖动后位置也存对了（`left=909.6, top=340`）。

撤回是因为**做出来也没用**。我的硬约束是"别被反作弊当成外挂"，这条约束砍掉了悬浮窗的两个核心价值：

| 原本想给的价值 | 为什么给不了 |
|---|---|
| 游戏里随手看占用 | 独占全屏会被盖住，要覆盖必须注入 DLL + Hook D3D → 必封 |
| 回答"我是不是掉帧了" | 需要帧率，帧率要 PresentMon 定向监控游戏进程 → 反作弊敏感 |

砍完只剩"窗口化游戏下也能看占用"，而窗口化下 Alt-Tab 回主界面只要一秒，主界面数字更大更清楚。**残余价值不成立，撤。**

顺手留了档，其中三个坑对任何 WPF 可拖动窗口都适用：
1. `DragMove()` 内部是模态循环，`MouseLeftButtonUp` 根本不会派发回来 → 改用 `LocationChanged` + 600ms 节流；
2. `Percent` 属性没钳制，会出现"颜色是对的、数字是 123%"；
3. 配置存 `left=1400` 但窗口出现在 x=1750——这是 125% 缩放下的设备无关单位换算，不是 bug。

这三条和那次撤回，比悬浮窗本身值钱。

## 五、AI 的两个系统性缺陷

574 个测试跑下来，我发现 AI 生成的代码有两类错误会**反复出现**，而且不是偶发：

### 缺陷一：默认只取第一个

| 版本 | 症状 | 根因 |
|---|---|---|
| v2.1.3 | VXE 鼠标电量显示"未知"（协议是对的、设备是好的） | `FindCompxPath()` 用了 `FirstOrDefault()`，只问第一台候选设备，而机器上两台同 VID 设备中坏的那台恰好排在前面 |
| v2.2.2 | 蓝牙耳机连上后，有线耳机从外设页消失 | `BuildHeadset` 用 `FirstOrDefault()` 只取第一个音频端点，蓝牙端点排前面，有线直接被丢掉 |

**两处 bug 隔了两天，写法一模一样。** 这不是巧合——`FirstOrDefault()` 是"能跑通"的最短路径，AI 在没有明确要求"要考虑多个候选"时会稳定地选它。

我的对策：凡涉及硬件枚举、设备列表、多实例的地方，需求里必须写死"要遍历全部候选、逐个试、第一个不应答换下一个"，并且**这条必须有对应测试**。

### 缺陷二：状态有多个真源时不会收敛

v2.1.2 的 bug：从总览进外设页再返回，两个页面叠在一起；"返回"按钮点了没反应。

根因是页面可见性被 XAML 的绑定和 C# 里的赋值**同时控制**。人能凭直觉发现"两处都在管同一件事"，AI 不会——它只保证自己新写的那处是对的。

我的对策：加一条 `PageRouter` 作为可见性的**唯一真源**，其余地方只读不写；再加一条**源码级测试**，直接读 `MainWindow.xaml` 校验导航项顺序与路由下标一致，防止以后有人加页面时写岔。

## 六、我用来兜底的四条规矩

写进 `AGENTS.md`，每次会话都生效：

1. **失败必须可见**——所有会改系统的操作，Apply 之后必须回读确认；回滚失败要明确报错，绝不静默显示"已还原"。
2. **不可观测的不报结论**——读不到电量就显示"未知"；内存释放量以系统可用内存实测为准，不拿逐进程合计（会因共享页面重复计数虚高数倍）冒充。
3. **口径要有测试锁死**——"多少算紧张""什么颜色算红"这类判定全部落到独立类里，用单测钉住，改实现不能改口径。
4. **不做静默安装**——不注入进程、不装驱动、不改系统服务。这条既是安全，也是上一条撤回的由来。

第 2 条最反直觉，但最有用：**工具最容易骗人的地方，不是算错，是"看起来算对了"。**

## 七、这套方法的天花板

得说清楚它不能干什么：

- **AI 不会替你做取舍。** 悬浮窗那次，AI 效率极高地把东西做出来了，但它不会问"这东西有存在的必要吗"。该撤还是得我撤。
- **AI 不会替你定义"对"。** 显存判定最初用"总容量"当分母，看起来合理，实际被别的程序占满时会误判。把分母改成"实时剩余"这个决定，是我盯着自己机器上的一次误判才想明白的。
- **测试数量不等于质量。** 574 个用例里，真正拦住问题的是我明确要求加的那些（坏片定位、第一台设备不应答、越界读数钳制），AI 自动补的边界测试质量参差。
- **文档债会累积。** 4 天写 6 篇 docs，一旦停下不同步，第二天 AI 就会照着过期文档写新代码。

---

## 八、最后

如果用一句话总结这 4 天学到的东西：

> AI Agent 把"写代码"的成本压到了接近零，于是**瓶颈整体前移到了"想清楚要什么"和"判断做得对不对"**。

它让我一个人能扛 1.86 万行的工程量，但项目里每一个"不做"、每一次撤回、每一条口径，都是人定的。

这也是我认为 AI 时代更稀缺的能力——不是会写多少代码，而是**在一堆能跑的实现里，认出哪个是正确的**。
