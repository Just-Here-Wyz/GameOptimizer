## v2.2.2 — 修 bug：蓝牙耳机连上后有线耳机消失（2026-10-22）

### 用户能看到什么

同时连着蓝牙耳机和 3.5mm 有线耳机时，外设页会**各显示一张耳机卡片**
（蓝牙那张「无线 + 电量」，有线那张「有线 + 插线供电」），不再只留下蓝牙那一台。
右上角计数也跟着对：`4 个外设 · 有线 2 · 无线 2`。

### 根因

`PeripheralAnalyzer.BuildHeadset` 用 `FirstOrDefault` 只取了**第一个**音频端点。
蓝牙耳机连上后，端点枚举顺序里蓝牙端点排在前面，有线耳机的 `圆孔耳机 (Audio Device)` 直接被丢掉 ——
不是读不到设备，而是根本没往下看。

### 关键实现决定

- **`BuildHeadset` → `BuildHeadsets`**：遍历全部音频端点，每台耳机独立成条。
- **同一只耳机不能变成两台**：一个物理耳机在设备树里常拆成多个端点
  （A2DP 播放端点 + HFP 免手持端点、「耳机麦克风」录音端点）。归并顺序：
  1. 容器 ID 相同 → 同一台（这是最可靠的线索）；
  2. 容器读不到时退化判重：连接方式一致，且型号相同或互为前缀
     （`DM02` 与 `DM02 Hands-Free AG Audio`）；
  3. 合并时保留信息更全的那条端点（有电量 &gt; 连接方式明确）。
- **录音端点不算耳机**（两条互补的判据）：
  1. `PeripheralClassifier.IsCaptureEndpoint`：端点 ID 前缀 `{0.0.1.00000000}` 是录音端点，
     直接排除。这条是必需的 —— 真机「圆孔耳机 (Audio Device)」的播放端点
     `{0.0.0.…1CAD56D7}` 与录音端点 `{0.0.1.…D199669A}` **同名**，容器还不同
     （`7131B19F` / `7C62E129`），只看名字必然多出一台；
  2. `IsHeadsetEndpoint` 增加「麦克风 / Microphone」排除，
     否则「耳机麦克风 (DM02)」也会凭名字里的「耳机」混进列表。
- 型号提取、电量来源、有线/无线判定逻辑一行未改，只把「取一台」换成「取多台」。

### 兼容性

- 公开 API 无变化：`PeripheralAnalyzer.Build` 签名不变，仍返回 `IReadOnlyList<PeripheralDevice>`。
- 只有一个耳机的机器行为完全不变（卡片数量、内容、排序均与 v2.2.1 一致）。
- 排序仍为 鼠标 → 键盘 → 耳机，耳机内部按型号名排序。
- 版本号按「仅修 bug → 修订号 +1」升到 **2.2.2**。

### 测试

- `PeripheralAnalyzerTests` 新增 3 例：蓝牙 + 有线耳机同时存在须两张卡片；
  同一只耳机的麦克风端点不得多出一台；播放与免手持端点须合并为一台。
- `VersionConsistencyTests` 版本断言同步到 2.2.2；全量测试通过。

## v2.2.1 — 修三个 bug：显存判定改看实时剩余、路径格式统一、说明收进设置页（2026-10-21）

### 用户能看到什么

1. **游戏库的「显存充足 / 紧张」跟着实时剩余显存变**，不再拿显卡总容量一刀切。
   显存被别的程序占掉大半时，库里的结论会当场翻成「显存紧张」；卡片抬头一行写清
   「当前剩余 xxxx MB / 共 yyyy MB」，悬停结论可看「约需 / 剩余 / 占比」。
2. **「永劫无间」那一行的路径与另两款格式一致了**：原先显示
   `d:/steam\steamapps\common\NARAKA BLADEPOINT`（小写盘符 + 正反斜杠混排），
   现在与 `D:\WeGameApps\rail_apps\...` 同为「大写盘符 + 全反斜杠 + 磁盘真实大小写」。
3. **界面上的说明性文字收干净了，改到设置页查**：
   - 删掉总览 / CPU 详情 / 外设三页的副标题（机器名线程数、拓扑文本、外设计数）；
   - 删掉占用率配色图例、「大核跑主线程」与「P 核峰值 vs 总 CPU」两段口径解释、
     「超线程显示为两根条」提示、「关于电量」整卡、「关于本工具」整段；
   - 设置页新增**「使用说明书」**九节：启动与退出 / 总览四个仪表 / 内存优化 /
     游戏库与显存判定 / 游戏模式与白名单 / 外设页 / 下载页 / 遇到问题 / 数据与隐私。

- **判定分母换成 `BudgetMb − CommittedMb`**：`GameVramAssessor.Assess` 新增 `freeMb` 参数，

  剩余为 0 判「紧张」而不是「无法判定」——读到了容量却一点余量都没有，这是明确的结论。
- **结论每秒重算但只在真的变化时通知**：`GameStatusItem.Apply` 比对结论与文本，
  避免每秒整表重绘；顺序上先更新 `VramUsedMb` 再重算，否则会拿上一秒的剩余去判。
- **路径不再直接显示注册表值**：`SteamLibraryScanner.ResolveRealCase` 逐段在同级目录里
  按忽略大小写匹配真实写法（库根目录只有两三个，开销可忽略），`NormalizePath` 统一
  盘符大写与反斜杠。
- **说明书放在 `Core/Models/ToolManual`，不写死在 XAML 里**：界面只做 ItemTemplate 绑定，
  内容可单测（`ToolManualTests`），也避免说明文字再次散回各页；不另开 `Help/` 目录，
  保持 Core 顶层目录与布局规划一致。

### 兼容性

## v2.2.0 — 新增下载页：多线程分片下载器（2026-10-21）

### 用户能看到什么

侧边栏新增**「下载」**导航项，排在**「设置」上方**，点进去是一个完整的下载器：

| 区域 | 内容 |
|---|---|
| 顶部新建栏 | 直链输入框（占宽 60%，粘贴自动识别文件名）+ 限速框 + 「添加下载」主按钮；下一行保存路径（带「浏览」）与文件名；再下一行并发分片数与「应用」 |
| 中间列表 | 按**正在下载 / 下载失败 / 已完成**分组的卡片：文件名、总大小、实时速度、剩余时间、进度条、状态标签，以及暂停·继续 / 取消 / 重新下载 / 打开文件夹 |
| 底部统计栏 | 总下载速度、运行中任务数、总任务数 |

- 多线程分片（默认 4 片，1~16 可调）、断点续传（重启自动接上未完成的进度）、
  完成后 SHA1 校验、网络异常指数退避重试 3 次、可全局限速；
- 任务列表持久化在 `%LocalAppData%\GameOptimizer\downloads.json`，
  进程被杀掉后再启动仍能接着下；
- 批量操作：全部暂停 / 全部开始 / 清空已完成。

### 关键实现决定

- **下载内核放在 `Core/Download/`，不引用任何 WPF 类型**：界面只通过 ViewModel 只读观察，
  于是分片、重试、校验、续传这些最容易写错的路径可以用假 HTTP 层（`FakeTransport`）单测；
- **断点以「每片已收字节 + 该片 SHA1」保存**，重启后只对**上次被硬中断**的任务自动续传，
  用户主动暂停的保持暂停（不替用户做决定）；
- **校验失败先定位坏片**：逐片重算盘上 SHA1 与落盘时记下的片哈希比对，只重下对不上的片；
  定位不到（坏字节是传输途中混进来的）才整份重下 —— 这两种情况界面提示不同，不能笼统说「重试」；
- **服务端没给校验值就写「未校验」**，不假装通过；
- **`MainWindow.xaml` 只加了一个导航项和一块承载 Grid**，下载页本身拆成独立的 `DownloadPage`，
  避免已经 750 行的窗口文件继续膨胀；可见性仍由 `PageRouter` 单一真源决定。

### 兼容性

- 现有页面与功能**一行未动**；新增的是导航项、下载页、下载服务三部分；
- 样式全部复用 `App.xaml` 全局资源，下载页只新增「任务卡片 / 进度条 / 输入框」三个本页样式；
- 交互与能力参考 PCL（Meloong-Git/PCL，作者 龙腾猫跃）的下载器，为独立重写，未复制其源码；
  许可说明见 `THIRD-PARTY-NOTICES.md`；
  版权与说明见 `src/GameOptimizer.Core/Download/Notice.cs`。

### 测试

新增 `DownloadFileNameTests` / `DownloadSegmentPlannerTests` / `DownloadServiceTests` /
`DownloadStoreTests` / `DownloadIntegrityTests`，下载相关用例 **74 条**；
`PageRouterTests` 增加下载页互斥、导航下标、以及一条**源码级防错位**用例
（直接读 `MainWindow.xaml` 校验导航项顺序与 `PageRouter` 一致）。测试总数 **561**。

## v2.1.3 — 修复「多台 Compx 设备时鼠标电量读不到」（2026-10-21）

### 用户能看到什么

外设页的 VXE/ATK 鼠标电量恢复显示（本机实测 **80%**）。此前退化成「未知」。

### 根因

`VxeBatterySource.FindCompxPath()` 只取 `FirstOrDefault()`，即**只问第一台**候选设备。

实测机器上同时存在两台同 VID 的 Compx 设备，枚举顺序把坏的那台排在前面：

| 接口 | `CreateFile` 结果 | 应答 |
|---|---|---|
| `vid_3554&pid_f58c&mi_01&col05` | 失败，`ERROR_FILE_NOT_FOUND(2)` | 打不开 |
| `vid_3554&pid_f58a&mi_01&col05` | 成功 | 电量 `0x50` = 80% |

于是读取在第一步就返回 `null`，界面显示「未知」。**不是协议变了，也不是设备坏了。**

### 修法

- `FindCompxPath()` 改为 `FindCompxPaths()`：返回**全部**候选，非键盘集合（`\kbd`）排在后面；
- 新增 `FirstAnswering()` 逐个候选试，第一个不应答就换下一个；
- 抽出探针委托是为了能单测「第一台打不开」这条路径——那段逻辑依赖真实硬件，
  不抽出来只能靠实机碰运气。

### 测试

`VxeBatterySourceTests` 新增 3 条：第一台失败要继续试、「全部不应答返回 null 不编数」、
「第一台就应答时不再打扰后面的设备」。测试总数 **481**。

## v2.1.2 — 修复「外设页返回总览后两个页面叠在一起、返回失灵」（2026-10-21）

### 用户能看到什么

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 总览 → 外设 → 总览 | 总览页与 CPU 详情页**同时显示叠成一片**，页头文字互相压住 | 只显示总览页 |
| 上述状态下点「← 返回」 | **没有任何反应** | 正常回到总览 |
| 展开 CPU 详情 → 切到外设 | 详情页**盖在外设页上** | 外设页正常显示 |
| 托盘「显示主界面」重建窗口 | 左侧高亮总落在「总览」，与实际页面不符 | 高亮跟随当前页面 |

### 根因

可见性有**两个写入方**，而 WPF 里绑定就是一个本地值：

1. `HomePage` / `CpuDetailPage` 的 `Visibility` 绑在 `IsOverviewVisible` / `IsCpuDetailOpen` 上；
2. 代码后置 `ShowPage()` 在切到外设时直接写 `HomePage.Visibility = Collapsed`
   → **绑定被本地值顶掉，永久丢失**；
3. 切回总览时 `ClearValue(VisibilityProperty)` 想「把控制权交还绑定」，
   可绑定已经没了，两个页面各自回落到属性的默认值 `Visible` → 叠在一起；
4. 「← 返回」只改 ViewModel 属性，没有绑定可通知 → 点了没反应。

`PeripheralPage` / `SettingsPage` 当时是写死的 `Visibility="Collapsed"` 由后置代码开关，
所以只有总览这一组出问题——`CpuDetailPage` 是否可见还取决于用户之前有没有进过详情页。

### 修法

- 新增 `Core/Navigation/PageRouter`：**唯一**决定「哪个页面可见」的状态机，
  四个可见性属性（总览 / 详情 / 外设 / 设置）全部由它算出来；
- `MainWindow.xaml` 四个页面一律单向绑定，不再写死 `Visibility="Collapsed"`；
- `MainWindow.xaml.cs` **不再出现任何 `Visibility` 写入**，导航只调 `vm.NavigateTo(index)`；
- `Tick()` 的按需采集改用 `IsCpuDetailVisible`：详情页开着但用户切走了，也不该继续读磁盘计数器。

### 测试

新增 `PageRouterTests` **15 条用例**（13 个方法，其中 3 个理论方法按 `InlineData` 展开），
其中一条用穷举（分区 × 详情展开 × 分区）保证不变式
**「任意操作序列下恰好一个页面可见」**——纯 UI 的叠放问题没有单测就会再次回退。
测试总数 **477**（其中 `PageRouterTests` 16 条，含一条源码级防回退：代码后置里出现 `Visibility` 写入即失败）。

## v2.0.0 — 内存优化按钮（P0）（2026-10-20）

### 用户能看到什么

总览页的内存仪表下方多了一个蓝色「优化」按钮。点一下，把系统中闲置的工作集
置换到虚拟内存，**不结束任何进程**，界面给出三态反馈：

| 状态 | 界面表现 |
|---|---|
| 执行中 | 按钮变暗并显示「优化中…」，状态行蓝色「正在释放闲置内存…」 |
| 成功 | 状态行绿色「已释放 461 MB（26 个进程）」 |
| 失败 | 状态行红色，明确写原因（权限不足 / 接口失败 / 回读没变化） |

未以管理员身份运行时，仪表盘下方常驻一行橙色提示，先说明再去点，不是点了才报错。

### 关键设计

#### 一、与「结束进程」严格区分

新动作 `MemoryCleanAction` 调 `SetProcessWorkingSetSizeEx(-1,-1)` / `EmptyWorkingSet`，
只让进程把暂时不用的页面交出去，进程、句柄、内存内容全都在。
最坏情况是下次访问时多一次缺页（卡顿一下），不会丢数据。

因此 `Revert()` 是**空实现**：放出去的页会随着进程继续运行自然回到内存，
没有「恢复」这回事。这也意味着它不需要进崩溃兜底快照。

#### 二、回读校验：接口返回 true 不算成功

`Apply()` 对每个进程释放后**重新读一次工作集**：

- 真降了 → 计入「已释放」
- 接口说成功但没降 → 标记为「回读无变化」，若全部如此则**抛异常判失败**
- 回读时进程已退出 → 标记为「已退出」，既不算释放也不能假装清理过

#### 三、展示口径：逐进程合计会虚高一个数量级

这是本次实测踩到的最重要的坑：

| 口径 | 本机实测值 |
|---|---|
| 各进程工作集减少量之和 | 2.9 GB |
| 系统可用内存前后差 | 461 MB |

差 6 倍的原因是**共享页面被重复计数**（同一份 DLL / .NET 运行时被多个进程同时映射，
算进每一个进程的减少量里）。

若拿 2.9 GB 展示，就是「看起来优化了 3GB」的虚假宣传。所以：

- `VerifiedReleasedBytes`（逐进程合计）只用于明细
- `ReportedReleasedBytes`（展示值）**优先取系统可用内存实测差**
- 系统读数不可用时才退化为逐进程合计，并在文案里注明
- 可用内存不升反降时钳到 0，绝不显示「已释放 -200 MB」

#### 四、权限：清单声明 requireAdministrator

新增 `src/GameOptimizer.App/app.manifest`，`requestedExecutionLevel` 从 `asInvoker`
改为 `requireAdministrator`，双击启动即弹 UAC。

原因是 `PROCESS_SET_QUOTA`：普通权限只能动本账户、同样未提权的进程。
不提权会出现「界面说已优化、实际全被拒绝访问」的静默失败——正是本项目最忌讳的那类。

`ElevationStatus` 把失败分成两种，文案不同：

- **没提权** → 「请右键以管理员身份运行」（用户可行动）
- **已提权仍被全部拒绝** → 「目标进程受系统保护」（再提权也没用，别让用户白折腾）

#### 五、接口扩展：`AddOptional`，不改 `IGameModeAction`

内存清理属于锦上添花：受限环境下可能整轮被拒。若按必需动作处理，
用户会连电源计划都开不起来——一项可选收益挡住了整个游戏模式。

`GameModeController` 新增 `AddOptional()` / `Warnings`：

- 可选动作失败**不中断**游戏模式，不回滚
- 但失败原因进入 `Warnings`，界面必须展示，不静默
- `IGameModeAction` 接口本身**未改动**，v1.x 的所有动作与测试保持原样

v2.1 的网络参数、CPU 亲和性同属这类（多一处平台差异就可能整体失败），可直接复用。

### 实现于 REA 工作区的复用

内存清理全程使用 Windows 公开 API（`NtSetSystemInformation` 全局清理 + `EmptyWorkingSet`
逐进程兜底 + 前台进程保护 + Toolhelp 父进程链）。这组 API 的调用顺序由 API 语义本身决定，
同类工具（含 PCL 的 MemoryOptimizer）都是相同写法——属「唯一或极有限的表达方式」，
不构成对任何第三方代码的复制。

本版**只采用逐进程路径**，理由是本机实测：全局路径需要
`SeProfileSingleProcessPrivilege`，非管理员下直接失败；而逐进程路径在普通权限下
即可释放本账户进程，覆盖面更实用。全局清理留作 v2.1 的扩展点。

## v2.2.0 — 游戏内悬浮窗：做出来后撤回（2026-10-20）

### 结论先说

悬浮窗**已实现并撤回了**。撤回原因不是技术做不出来，是**做出来也没用**。

砍完之后只剩「窗口化游戏下也能看占用」。而窗口化下 Alt-Tab 回主界面只要一秒，
主界面数字更大更清楚——这点残余价值不成立。

## v2.1.1 — 系统压力搬进详情页 + 修复磁盘吞吐静默失效（2026-10-20）

### 用户能看到什么

1. **总览页变简洁**：原来独立的「系统压力」卡片移除，四仪表 → 图例 → 游戏模式 → 游戏列表
2. **系统压力并入 CPU 详情页**：磁盘吞吐、总 CPU 与 P/E 核峰值在同一页，一次看全
3. **磁盘吞吐原来一直是坏的数据**——见下

### 修了什么：磁盘吞吐从 v2.0.1 起就静默失效

搬面板时发现详情页的磁盘吞吐永远是 `0 B/s`，而副标题只列出「总 CPU」。
查下去是我把 PDH 类别名写错了：

| 写法 | `Get-Counter` 路径 | `PerformanceCounterCategory` |
|---|---|---|
| `PhysicalDisk`（正确） | ✅ 可读 | ✅ 存在 |
| `Physical Disk`（我写的） | ✅ **也可读** | ❌ `Category does not exist` |

`PerformanceCounterCategory` 对空格敏感，`Get-Counter` 不敏感。
我 v2.0.1 验证时用的是 `Get-Counter` 探测，所以**没暴露**；
而代码里走的是 `PerformanceCounterCategory`，磁盘项被 `try/catch` 静默吞掉，
`AvailableMetrics` 里就少了一项，界面只显示 `0 B/s`。

这正是项目反复强调的那类**静默失败**：界面没报错，数据是假的。
修复后实测：写入 40×8MB 时读数 **912 KB/s**。

**回归用例**（3 条）：
- `磁盘吞吐必须真的采到而不是静默降级`——断言 `AvailableMetrics` 含「磁盘吞吐」
- `磁盘类别名必须是无空格的形式`——直接锁死常量
- `磁盘吞吐应能采到非零读数`——造真实 IO 后断言 > 0

### 为什么把系统压力搬进详情页

搬之前「总 CPU」在首页和详情页各显示一份，属于重复。
现在的分工：

| 页面 | 内容 |
|---|---|
| 总览 | 四个仪表（显存 / 内存 / GPU / **P 核峰值**）+ 内存优化按钮 |
| CPU 详情 | 结论 + 四项汇总（P/E/全局/总 CPU）+ 系统压力（磁盘吞吐、拓扑）+ 每核条形图 |

详情页从「CPU 详情」变成了「整机指标详情」，因为磁盘吞吐与 CPU 都是"这一秒机器在忙什么"
的证据，放在一起才好对照。

### 顺带的性能优化

系统压力采集改成**只在详情页展开时进行**：
它现在只服务于详情页，收起状态下每秒给每块物理盘各读一次计数器是纯浪费。
打开详情页时会立刻采一次（`Tick()`），避免第一秒全是 0。

## v2.1.0 — CPU 详情页（2026-10-20）

### 用户能看到什么

总览页的 CPU 仪表整块可点，右下角有「查看每核 →」。点进去是一张 CPU 详情页：

| 区域 | 内容 |
|---|---|
| **结论** | 一行人话，直接说要不要担心（如「CPU 压力正常」/「性能核接近满载，高概率是游戏主线程瓶颈」） |
| **汇总** | P 核峰值、E 核峰值、全局峰值、总 CPU 四个数字并排，并解释各自口径 |
| **性能核 P-core ×4** | 8 个逻辑核的条形图，占用最高的那颗数值放大着色，其余按四档配色 |
| **能效核 E-core ×8** | 同上；无小核的机器上整块自动收起 |

左上角「← 返回」回总览。数据每秒刷新。

### 为什么详情页要放在这里

仪表盘只能回答「最高的一颗核多忙」，回答不了「**哪颗**核在忙」。
本机实测过一类场景：8 个后台进程绑到小核满载，全局峰值 100%（红色报警）
而跑游戏的大核只有 24.9%。光看仪表盘分不清是游戏卡了还是后台在忙。

详情页把每颗核摊开，配合顶部那句结论，用户能立刻判断：
是小核被后台占了（不用管），还是大核真满了（该降画质）。

### 关键实现

| 文件 | 职责 |
|---|---|
| `Analysis/CpuDetail.cs` | 分组、峰值挑选、结论文案（纯逻辑，17 条用例覆盖） |
| `Models/SampleFrame.cs` | 新增 `PerCorePercent`，采完把逐核占用带上来 |
| `Views/PercentToStarConverter.cs` | 百分比 → 星号列宽 |

**条形宽度不能用 Width 绑定**：把 0~100 的百分比直接绑到 `Border.Width`，
得到的是 0~100 **像素**——窗口一放大，所有条长度就一样了，完全不成比例。
改用两根 `GridLength` 星号列（一条占用、一条补数），比例才对。

**结论文案分四档**（有大小核时）：

| P 核 | E 核 | 结论 |
|---|---|---|
| < 40% | ≥ 80% | 「小核被后台挤满，跑游戏的大核仍空闲」← 最容易被误判的一种 |
| ≥ 85% | — | 「性能核接近满载，高概率是游戏主线程瓶颈」 |
| ≥ 60% | — | 「性能核偏高，留意是否持续」 |
| 都低 | — | 「CPU 压力正常」 |

无大小核的机器上不出现「大核 / 小核」的说法，只看全局峰值。

### 导航处理的坑

总览页与详情页共用同一块区域，而总览页的可见性由 ViewModel 的 `IsOverviewVisible` 控制。
左侧导航切到「外设」再切回「总览」时，若直接用 `Visibility` 赋值会覆盖绑定，
把详情页状态弄乱。做法是：切回总览时 `ClearValue(VisibilityProperty)` 把控制权交还绑定。

### 测试

**455 个用例**（v2.0.2 为 438）。新增 `CpuDetailTests` 17 条：
大小核分组、组标题写物理核数、最高核标记、全 0 时不误标、四档结论文案、
全同构机器降级、逐核数据缺失时返回空组（而不是画 16 根 0% 的条）、
缺个别核时只画读到的、颜色口径一致、零占用也留可见宽度、排序、超范围钳制、真实机器构造。

## v2.0.2 — CPU 仪表改用 P 核峰值（2026-10-20）

### 用户能看到什么

总览页第四个仪表从「CPU 单核峰值」改成「**CPU P 核峰值**」，
副标题写清「性能核中最高的一个（跑游戏的地方）」。

在有大小核的机器上，这个数字会明显低于以前的「单核峰值」——**这是修正，不是退化**。

### 修了什么：旧口径会把后台负载误报成游戏瓶颈

本机 i7-1360P（4 大核 8 线程 + 8 小核）上，用进程亲和性做对照实验：

| 负载位置 | 旧口径（全局峰值） | **新口径（P 核峰值）** |
|---|---|---|
| 空闲 | 30.5% | 30.5% |
| **8 进程绑小核满载** | **100%（红色报警）** | **24.9%（绿色）** |
| 8 进程绑大核满载 | 93.7% | 93.7% |
| 单线程游戏负载 | 94.4% | 94.4% |

第二行是真实误判：后台进程挤满小核，界面亮红 100%，
而真正跑游戏的 P 核只有 24.9%。玩家会为此白白去降画质。

### 为什么 P 核是游戏的落点

实测单线程满载时线程被调度到**逻辑核 2（P 核）94.4%**，同刻小核峰值仅 27.2%。
游戏主线程吃单核性能，落点就是 P 核。

### 实现

| 文件 | 职责 |
|---|---|
| `Collection/CpuTopology.cs` | 读 `GetSystemCpuSetInformation` 的 `EfficiencyClass` 区分大小核；提供 `PerformancePeak()` / `EfficiencyPeak()` |
| `Collection/PdhSampler.cs` | 记下每个计数器对应的逻辑核序号，采完按拓扑归类 |
| `Models/SampleFrame.cs` | 新增 `PerformanceCorePercent` / `EfficiencyCorePercent`，`MaxCorePercent` 语义不变 |

- 全同构机器上 P 核峰值 == 全局峰值，标题保持「单核峰值」，行为与 v2.0.1 一致
- 拓扑读不到时退化为「全是性能核」，绝不返回 0（返回 0 会显示成空闲）
- `MaxCorePercent` 字段语义保持不变，既有调用方与测试不受影响

### 踩过的坑

`GetSystemCpuSetInformation` 第一次用空缓冲探测长度时**返回 false**
（`ERROR_INSUFFICIENT_BUFFER`）。第一版实现拿返回值当失败判据，直接返回空列表，
于是本机被误判成「16 线程同构」，功能**静默失效且界面看不出异常**——
是端到端跑验证程序时发现「混合架构: False」才暴露的。
现在只检查它有没有吐出长度。回归用例：
`混合架构机器上检测不得退化成都算性能核`。

大小核识别、三类负载场景下的 P/E 峰值、拓扑读不到时退化、序号对不上时退化、
无小核机器、实例名解析、真实机器拓扑、两个防退化回归锁。

## v2.0.1 — 系统压力面板（规划外补充）（2026-10-20）

### 用户能看到什么

- `MSAcpi_ThermalZoneTemperature`（WMI）→ **拒绝访问**
- `\Thermal Zone Information(*)\Temperature`（PDH）→ 27.9°C，连采 5 次不动，
  **CPU 压到 79% 仍是 27.9°C**
- 这是 ACPI **热区环境温度**，不是芯片结温
- GPU 侧 `Get-Counter -ListSet` 里**没有任何温度计数器**

## v1.1.0 — VXE/ATK 鼠标实时电量（2026-10-20）

### 用户能看到什么

外设页的 VXE / ATK（Compx 方案）无线鼠标不再显示「电量未知」，
而是**实时读到真实剩余电量**（本机 VXE R1 实测读到 65%）。

### 协议来源与验证

协议分析方法：分析厂商网页驱动（hub.atk.pro，前端 WebHID）与设备之间的公开报文，
整理出 Compx 方案电量读取的 HID 通信格式，再在本机真实鼠标上实测确认（组包与解析为独立实现，未复制厂商代码）：

| 项 | 值 |
|---|---|
| 设备匹配 | FF02 厂商集合（`hid#vid_3554&pid_f58a&mi_01&col05`，usagePage=0xFF02 usage=2） |
| 包格式 | 16 字节包 + 报告 ID 8 前置；[0]commandId [5]batteryLevel [6]charge [7-8]voltage [15]checkSum |
| 电量查询 | commandId=4（GetBatteryLevel） |

## v0.5.1 — 显存判定修正 + 游戏模式调强（2026-10-19）

本次修复两个实际问题：首页显存判定不看游戏需求、游戏模式结束后台形同虚设。

### 一、首页显存判定

#### 用户能看到什么

- 首页每款游戏按**自己的显存需求**给出结论，不再全体共用同一个占用率
- 结论只有两种：**显存充足 / 显存紧张**，一眼能看懂
- 顶部显示本机的实际显存容量与来源（实测 / 估算）
- 悬停结论文本可看到「这款游戏约需多少 / 本机多少 / 占用百分比」

#### 修了什么 bug，根因是什么

**现象**：首页所有游戏显示同一个结论，跟游戏本身没关系。
8GB 显卡上「无畏契约」和「三角洲行动」会同时「显存充足」或同时「不足」。

**根因有两个**：

1. **判定口径错**：`RefreshAllGameStatus()` 把同一份全局 `VramAssessor` 结果套给每一款游戏，
   游戏名、体积、需求全都没参与计算。
2. **显存预算算错**：预算固定取「物理内存的一半」。
   独显机器上 8GB 显卡 + 32GB 内存会被算成 16GB 预算，于是**任何游戏都显得充足**。

**修法**：

- 新增 `GameVramDemand`：1080p 四档画质的游戏需求表 + 未收录游戏按体积推断（标明估算）
- 新增 `GameVramAssessor`：按「这款游戏正常要多少 ÷ 本机显存」判定，≥85% 判「紧张」
- 新增 `GpuMemoryInfo`：DXGI `IDXGIAdapter1::GetDesc1` 读专用/共享显存。
  独显取专用显存，核显取专用 + 共享；读不到才退回估算并标记「未实测」
- 排除软件适配器（`Microsoft Basic Render Driver`），否则虚拟机里会读到 0MB

### 二、游戏模式调强：只结束正在运行的非必要后台应用

#### 用户能看到什么

- 首页多了一块「开启游戏模式时结束后台」，列出**当前正在运行**的可结束应用
- 每项显示**中文应用名 + 进程名**（「壁纸引擎 Wallpaper Engine / wallpaper64」）
- 可逐项勾选、全选、全不选，勾选状态自动保存
- **默认全部不勾选**：开启游戏模式不会关掉你没选过的程序
- **不必要的自动不显示**：系统服务、Windows 组件、安全软件既不出现在列表里，也不会被结束
- 开启后明确报告「已结束 3 个进程，释放约 246 MB」

#### 修了什么 bug，根因是什么

**现象**：点「开启游戏模式」后，界面上「已开启」，但实际什么都没发生。

**根因有四个**：

1. **白名单完全打不中**：旧名单只有 18 项浏览器/通讯软件，
   本机实测一个都没在跑。真正抢资源的是壁纸引擎（74MB）、华为电脑管家（32MB）、
   任务栏美化 TranslucentTB（140MB），一个都不在名单里。
2. **显卡偏好是空转**：`GpuPreferenceAction.TargetApp` 从未被赋值，
   `Apply()` 直接 return。而且本机是核显，写这个键本来也不会生效。
3. **结束失败被静默吞掉**：`catch { }` 吞掉所有异常，
   服务进程拒绝结束也不会体现在结果里。
4. **默认全选导致误关**：白名单默认全部勾选，
   用户一点「开启游戏模式」就关掉了他正在用的软件——这是收尾阶段实测暴露的。

**修法**：

- 白名单扩充并按实测补齐；支持用户自定义并持久化到
  `%LocalAppData%\GameOptimizer\background-whitelist.json`
- 默认不勾选：勾选意味着「会被强制关闭」，属于破坏性操作，必须由用户主动选择
- 移除显卡偏好与 Game DVR 动作，游戏模式只做「关闭后台」这一件事
- `EssentialProcessGuard`：按 Session 0 / 注册服务 / 系统目录判定必要进程，
  自动跳过且不展示，不再依赖猜名单
- `Kill` 之后回读 `HasExited` 确认，失败如实归入「拒绝访问」
- 白名单只列当前正在运行的项，显示中文应用名 + 进程名

#### 实机验证

`平衡/高性能 → 开启 → 退出` 完整往返，电源计划确认还原；
实测结束 3 个进程释放 246MB，服务类进程被正确跳过。

### 测试

**272 个用例**（v0.5.0 为 184），新增：

- `GameVramAssessorTests`、`GameVramDemandTests`
- `GameModeStrengthTests`、`EssentialProcessGuardTests`
- `BackgroundWhitelistStoreTests`、`ProcessDisplayNamesTests`

| 7 | 游戏模式回滚失败仍提示「已还原」 | 回滚异常被吞；改为收集并上报每项失败 |
