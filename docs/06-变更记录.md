## 未发版 — ① 关闭游戏模式后由用户选择恢复哪些进程（2026-10-26）

版本号未定，改动已并入源码、尚未发版（按 `docs/03` 的规则，版本号由用户设定）。

### 用户能看到什么

1. **关闭游戏模式后弹独立窗口**「游戏模式已关闭 · 选择需要恢复的后台进程」：
   每行显示应用名、exe 名、发布者（读得到时）、简短说明、恢复资格与原因，行首一个复选框。
2. **全选 / 取消全选**：一个按钮，文案随状态在「全选」「取消全选」之间切换；
   只作用于可恢复项，被跳过的项不会被拉进恢复队列。
3. **恢复所选**：只启动勾选的进程，**逐项启动**（约 0.4 秒间隔），过程中显示「正在恢复 3/5：chrome.exe」，
   结束后给出「已恢复 5 项，跳过 2 项，失败 1 项。」并附逐项明细 + 完整日志路径。
4. **取消**：本次一个进程都不启动，游戏模式不会重新开启，快照与白名单原样保留（下次启动仍会问）。
5. **没有可恢复项就不弹窗**：首页状态行直接说「游戏模式：已关闭，没有需要恢复的后台进程」。
6. **首页不再刷一屏红字**：关闭结论只有一句摘要，逐条异常（含类型与错误码）写进
   `%LocalAppData%\GameOptimizer\restore-log.txt`。

### 为什么要改

- 用户要求「关闭后自己挑要恢复哪些」：原来的实现一律全恢复，等于没有选择权；
  一次性 `Process.Start` 十几个应用还会互相抢磁盘，界面卡死、启动互相拖慢。
- 原来的关闭流程把「还原电源计划」和「拉起进程」揉在一次 `Revert()` 里，
  想让用户选就必须先把这两件事拆开。

### 关键实现决定

- **顺序反过来了**：`ExitWithReport(deferProcessRestore: true)` 只关游戏模式（电源计划等），
  进程留到弹窗之后再恢复。先恢复再问，选择权就形同虚设。
- `EndProcessAction` 加 `AutoRestoreOnRevert`（默认 true，托盘退出 / 崩溃兜底仍全恢复），
  并抽出 `IProcessRestoreSource`（`PendingRestores` / `Restored`），
  控制器不再认识具体动作类，测试也不必真的结束一个进程才能验证延迟恢复。
- **恢复资格独立成纯函数** `ProcessRestorePlanner`：路径缺失 / 文件不存在 / `%SystemRoot%` 组件 /
  应用商店应用（WindowsApps、MSIX）/ 硬编码保护名单 / 重复目标 / 已在运行——一律跳过并写明原因。
  应用商店应用不做「猜包身份启动」，因为反推错了就是启动一个不相干的程序。
- **`ProcessRestoreRunner` 顺序执行**：可注入启动器与等待实现；同一时刻只允许一批（重复触发返回 null）；
  每条记录只启动一次；启动后**回读确认进程真的在运行**才计入成功，
  提交成功但没观察到 → 「未确认」，算失败。单项异常（含启动器抛异常）只影响该项。
- **选择状态只有一份**：`ProcessRestoreSelection` 按下标存勾选状态，
  界面每行只是它的视图；「全选」「恢复所选」读同一份，不可能「看着都勾了、实际只恢复一半」。
  不可恢复项在 Core 侧就被拒绝勾选，不依赖界面禁用。
- **快照语义变成「还没成功恢复的进程」**：全部恢复完 → 删快照；部分失败或用户取消 → 只留剩余项，
  电源计划字段置空（那一步已经还原，留着旧 GUID 会在下次启动把电源设置再改一遍）。
  启动时的兜底提示也改了措辞：「上次关闭游戏模式后还有 N 个进程没有恢复」（不再说「未正常退出」）。
- **崩溃兜底也不再无条件启动**：`GameModeRecovery.Restore` 先过同一个资格判定，
  跳过项单独上报、且不算「没还原完」（否则快照永远清不掉、每次启动都追问）。
- 日志写入全程 `try/catch`：写不进日志只丢日志，不中断恢复（`ProcessRestoreLog` 承诺永不抛出）。

### 测试

新增 / 调整：`ProcessRestorePlannerTests`、`ProcessRestoreSelectionTests`、`ProcessRestoreRunnerTests`、
`GameModeDeferredRestoreTests`，`GameModeRecoveryTests` 补资格判定用例，
`GameModeStateStoreTests` 补旧版快照兼容。全部用注入的启动器与合成记录，**不启动也不结束任何真实进程**。
全量 **822 例通过**，构建 0 警告 0 错误；弹窗用 `--render restore` 离屏渲染验证过排版。

## v2.4.0 — ② 保护语义改为「勾选即保护，其余默认结束」（2026-10-25）

属于**功能性更新**，已随 v2.4.0 发布（2026-10-26）：`Directory.Build.props` 与
`VersionConsistencyTests` 的版本断言同步升到 2.4.0。

### 用户能看到什么

1. **浮窗里每行只留一个复选框**：「保护」。没勾的就是会被结束的，卡片右侧直接标
   「会结束 / 不会结束」，不用再点第二个按钮确认。
2. **计数与摘要改成结果口径**：顶部写「共 20 项 · 受保护 1 · 会被结束 19 · 无法识别 2」；
   总览页摘要写「受保护 1 项 · 启动游戏模式时将结束 19 项」；浮窗底部直接列名单
   （「将结束 19 项：cc-switch、ChatGPT、…」）。
3. **配置文件简化**：`background-whitelist.json` 升到 `schemaVersion: 3`，只存 `protected`。
   旧版的 `processes` / `endTargets` 都已并入默认行为，迁移时丢弃并给一条提示。
4. **游戏卡片有图标**：首页「已安装游戏」每条显示游戏自己的 exe 图标，取不到就退化成名称首字符色块。

### 为什么这么改

- 用户原话：「除标为保护进程外，其他直接默认为要结束的进程」。
  初版设计要用户逐个「标记为结束目标」，实际用起来是几十次点击，等于把功能废掉。
- **这比「默认不动」激进**，所以界面必须把后果写在明处：每行结果标签、底部名单预览、
  总览页摘要三处都在回答「这次会关谁」，不需要点了才知道。

### 关键实现决定

- `BackgroundTargetFacts` 去掉 `IsEndTarget`，`KillBlockReason.NotMarked` 与
  `DecideMarkable` 一并删除（没有「标记」这个动作了）。
  `Decide` 顺序：保护 → 系统关键 → 游戏本体 → 读不到路径 → 通过。
- `BackgroundProtectionState` 只保留 `Protected`；`BackgroundWhitelistStore` 写 v3，
  并给 `JsonSerializerOptions` 加 `DefaultIgnoreCondition = WhenWritingNull`——
  否则序列化会把 `"endTargets": null` 写进文件，让人误以为这字段还在起作用。
- `BackgroundProcessEntry.IsEndTarget` 改为派生值（`Verdict.Eligible`），不再有可写状态，
  界面与执行侧不可能再出现「显示会结束但实际不结束」。
- 迁移只保留 `protected`：v1 的 `processes` 与 v2 的 `endTargets` 在新规则下本来就属于结束范围，
  丢掉不改变行为；**但绝不倒成保护**，那会让用户以为游戏模式还在关那些程序。
- 首页游戏卡片补 `Icon` / `IconFallbackText`，与浮窗共用 `AppIconCache.ForPath`。

### 测试

`BackgroundWhitelistStoreTests` 按 v3 重写，`BackgroundProtectionTests` 的语义用例重写为
「默认结束 + 四道闸门」。全量 **760 例通过**，构建 0 警告 0 错误。

## v2.4.0 — ③ 后台进程白名单改为保护浮窗（2026-10-25）

同样属于**功能性更新**，已随 v2.4.0 发布（2026-10-26）。

### 用户能看到什么

1. **总览页不再铺一整块进程列表**：原来的「开启游戏模式时结束后台」面板撤掉，
   只留「管理后台进程」按钮 + 一行摘要（受保护几项、结束目标几项）。
2. **独立浮窗**：点按钮打开，可调整大小、搜索（应用名 / 进程名 / 路径 / 用途 / 发布者）、
   按状态筛选（全部 / 受保护 / 未保护 / 无法识别）、滚动查看，
   每行可展开看完整 exe 路径、文件描述、产品名称、版本与识别依据。
   列表**只列能管理的进程**：资源管理器、桌面窗口管理器、服务宿主这类系统关键项不出现
   （既不能保护也不能标记结束，列出来只是噪音），拦截仍由安全机制独立完成。
3. **进程信息变得可读**：原来只显示 `0dcloud`、`HwMdcCenter` 这种进程名，
   现在优先显示 exe 版本资源里的**文件描述 / 产品名称**，附进程名、发布者（公司名）、用途与状态。
   **有中文名就用中文**：三个来源（文件描述 / 产品名称 / 内置名）任一含中文就取它，
   例如版本资源全是英文的 `msedgewebview2` 会显示成「Edge 组件（WebView2）」；
   全都不含中文时保持原文（Spotify 不会变成「声田」）。
   读不出身份就写「未知应用」，用途认不出来就写「用途未知」，并给出识别依据。
4. **语义反转：勾选 = 保护**。勾上「保护」的进程，游戏模式绝不结束；
   没勾选只代表「没有主动保护」，**不会**因为取消勾选就被结束。
   要结束某个程序必须另外点「标记为结束目标」，且只有通过安全检查的进程才点得动。
5. **关闭浮窗什么都不做**：不开启游戏模式、不结束任何进程，也不丢设置（改动即时保存）。
   保存失败会在底栏红字写明原因，并提供「保存」按钮重试。

### 为什么这么改

- **旧语义与用户直觉相反**：「勾选 = 会被关掉」是最容易点错的设计——
  用户想保留某个程序，会本能地去勾它。改成「勾选即保护」后，
  误操作的方向从「误关程序」变成「误留程序」，代价小得多。
- **但「没勾选 = 可以关」同样危险**：默认状态是一个都没勾，
  若据此判定「都可以结束」，就是重演 v0.5.1 的默认全选事故。
  因此拆成两条独立的轴：**保护**（复选框）与**结束目标**（显式标记），
  并且结束目标默认清空。`未勾选` 只是「有资格」，不是「会被关」。
- **旧配置不能直接反转**：v1 文件 `{"processes":[...]}` 里的项含义是「会被结束」。
  迁移时按**原语义**搬进 `endTargets`，保护名单留空，并弹一条提示让用户核对；
  把旧勾选倒成「受保护」等于悄悄改掉用户的决定（他会以为游戏模式还在关那些程序）。
  结构认不出来的配置一律当空处理（一项都不关），同样给出提示。
- **「未知」必须写未知**：机器上真实存在 `0dcloud`、`cc-switch` 这类没有任何可查信息的进程。
  按名字猜用途会编出「可能是下载工具」这种假信息，因此宁可在界面上标黄写「用途未知」。
  能识别的来源只有四种：内置识别表（已知产品精确匹配）、系统目录路径、
  注册服务、exe 版本资源里的产品名 / 文件描述关键词；每条结论都带「识别依据」。

### 关键实现决定

- Core 新增：`Library/ProcessFileMetadata`（读版本资源，失败返回空对象）、
  `Library/BackgroundProcessPurpose`（用途识别与依据）、
  `Library/BackgroundProtection`（`ProtectionState` / `KillVerdict` / `BackgroundProtectionPolicy` /
  `BackgroundKillPlan` / `BackgroundProcessFilter`）、
  `Library/BackgroundProcessInspector`（扫描结果 → 展示模型）。
- `BackgroundWhitelistStore` 升级到 schemaVersion 2，新增 `LoadState()` / `SaveState()` 与迁移结果模型
  （`MigratedFromLegacy` / `Notice` / `Error`）；旧的 `Load()` / `Save()` 直接删除，
  避免留下一个含义含糊的「名单」入口。
- `BackgroundCandidateScan.ScanEntries()` 只返回**可结束候选**：
  系统关键进程（资源管理器、桌面窗口管理器、服务宿主等）在扫描阶段就被丢弃，不进列表。
  这类进程原本以 `SystemProtected` 只做展示，但用户明确表示「这些我根本不会去动，别占地方」；
  拦截与展示无关，`EssentialProcessGuard` 仍在执行侧独立拦。`BackgroundCandidateKind.SystemProtected`
  枚举值与 `BackgroundProcessInspector` 对它的处理保留，安全判据不因展示策略而削弱。
- 应用名解析（`BackgroundProcessInspector.ResolveAppName`）改为**中文优先**：
  在「文件描述 / 产品名称 / 内置名」中挑第一个含汉字的，都没有才按原顺序退化。
  内置名必须先用 `ProcessDisplayNames.HasName` 挡掉「未收录时退回进程名」的假中文。
  新增 `ContainsChinese`（只认汉字基本区与扩展 A），不引入拼音/翻译推断。
- 修 `AppIconCache` 图标提取：`SHGetFileInfo` 的**返回值只表示成功/失败，图标句柄在 `info.hIcon`**，
  原实现错把返回值当句柄传给 `CreateBitmapSourceFromHIcon`，必然失败，
  于是每一行都退化成「首字符色块」。顺带删掉无调用者的 `For(processName)`
  （旧面板删除后已成死代码，且内部有同一个错误），只保留按路径取图标的 `ForPath`。
- `EndProcessAction` 增加 `protectedNames` 参数：执行侧再拦一次受保护项，
  防止调用方绕过界面把受保护进程塞进目标列表；跳过的项单独记为 `ProtectedSkipped`
  并在 `Summary` 里说明。
- `EndProcessAction` 的初始名单改为空（`App.BuildGameMode`）：进游戏模式前从 `MainViewModel` 同步，
  不再用内置默认名单打底。
- 浮窗由 `MainWindow` 创建并持有（`OpenBackgroundManagerRequested` 事件），
  ViewModel 里不出现 `Window` 类型；重复点按钮只前置已有窗口，
  主窗口收进托盘时浮窗一起隐藏，主窗口真正关闭时浮窗一起关闭。
- `OffscreenRenderer` 新增 `background` 页面，便于离屏核对浮窗排版。

### 测试

新增 42 例（`BackgroundProtectionTests` + 重写的 `BackgroundWhitelistStoreTests`），
全量 **763 例通过**。覆盖：选中即保护、取消勾选不结束、未标记不结束、
必要进程拦得住、未知进程默认不动、旧配置迁移不反转语义、搜索与筛选口径、
元数据读取失败降级、保存失败可见、执行侧跳过受保护进程、
中文名优先（文件描述英文 + 产品名中文 / 元数据全英文但内置名含中文 / 纯英文不编造译名）、
扫描结果不含系统关键进程。

## v2.4.0 — ④ CPU 诊断页与 CPU 快速优化（2026-10-25）

属于**功能性更新**，已随 v2.4.0 发布（2026-10-26）：`Directory.Build.props` 与
`VersionConsistencyTests` 的版本断言同步升到 2.4.0。

### 用户能看到什么

1. **首页 CPU 仪表换了口径**：显示**整机总体占用率**，不再是「P 核峰值」。
   以前小核被后台程序挤满、大核只有 25% 时仪表显示 25%，看着很闲；
   现在显示真实的整机负载。P 核峰值没有消失，它挪到了 CPU 页的「高级详情」里，
   仍然回答「跑游戏的那颗核忙不忙」。
2. **点 CPU 卡片进入诊断页**：一行结论（正常 / 持续偏高 / 持续高负载 / 采样中 / 未知）
   + 当前占用 + 30 秒平均 + 最近 30 秒趋势折线 + 高占用进程列表 + 采样状态与数据完整性。
   页内二级导航「CPU 诊断 / 高级详情」，默认进诊断。
3. **「CPU 优化」是独立流程**：点按钮进入「轻量检测 → 逐项确认 → 执行 → 回读对比」，
   不再与「点卡片看诊断」抢同一次点击。候选默认**全部不勾选**，
   每条都写明实测占用、影响范围（会关掉这个应用）与恢复方式。
4. **结束后能回滚**：结束过的进程可以按原路径重新拉起，失败的逐条报出。
   只保证「重新启动这个程序」，不保证恢复窗口与未保存内容——这句话写在界面上。
5. **结果只报实测**：结束 0 个就写「没有进程被结束，系统状态未改变」并说明跳过 / 拒绝访问各几项；
   回读窗口内有效帧不足 5 秒的 3 帧就写「无法对比」，不拿优化前的数字充数。
6. **不碰系统与安全软件**：系统服务会话、Windows 组件、安全软件、游戏本体、本程序自身、
   读不到 exe 路径的进程一律不出现在可执行项里，并在附注里写明被排除的原因。
7. **说明书写清楚了**：设置页「使用说明书」新增「CPU 诊断与快速优化」一节，
   总览一节改掉了「CPU 取 P 核峰值」的旧说法。

### 为什么这么改

- **旧口径会误导**：`CpuCorePercent` 是 P 核峰值，把它改名成「CPU 占用」就是伪造读数。
  所以新增一路真实的总 CPU 采集，而不是重命名旧指标（有用例锁死这一点：
  XAML 里不允许再出现 `CpuCorePercent` 绑定到首页仪表）。
- **同一秒只读一次计数器**：PDH 的 `NextValue()` 给的是「距上次读取」区间的平均值，
  同一秒读两次，第二个数字算的是极短区间。因此把总 CPU 与磁盘吞吐拆成两个单项读取方法，
  由页面可见性决定读哪一项，而不是每次把两项一起读。
- **进程 CPU 只有一种可靠口径**：`TotalProcessorTime` 差分 ÷ 墙钟 ÷ 逻辑核数，
  与任务管理器同语义。PDH `Process\% Processor Time` 需要按实例建计数器，
  实例名随 PID 反复失效，实测重建开销更高。受保护进程读不到处理器时间，
  计入「读不到」而不是 0%（有单测锁死「不补零」）。
- **「持续」必须是连续有效窗口**：缺一帧或相邻帧间隔 >2.5 秒即断链，
  连续时长从断点之后重算。这是托盘隐藏 / 最小化造成采集中断后，
  界面不会凭空冒出「持续高负载」的原因。
- **离开页面清空历史**：页面不可见时本来就停采，把中断前后的数据拼成一段「连续 30 秒」是伪造。
- **快速优化不借道 `GameModeController`**：`Enter()` 会写游戏模式专用的崩溃兜底快照，
  借道会覆盖它，导致下次启动弹出错误的还原提示。所以只复用 `EndProcessAction`
  （内部已含 `EssentialProcessGuard` 与 `BackgroundProcessWhitelist`），
  并按原路径回滚。
- **优化流程打开时进程排名还没算出来**：进程占用需要两次采样。进入流程时会立刻补一帧，
  若此时仍无排名，界面标「进程占用列表还没有可用数据（进程占用需要两次采样），稍后重试」，
  并在下一帧排名就绪时**自动补检测**，不需要用户退出重进。

### 关键实现决定

- Core 新增：`Analysis/CpuLoadAnalyzer`（诊断规则）、`Analysis/CpuOptimizePlanner`（建议生成）、
  `Analysis/CpuOptimizeVerification`（前后对比文案）、`Analysis/CpuTrendGeometry`（趋势坐标换算）、

## v2.3.0 — 游戏模式体验：按钮反馈、双击提权、单实例、白名单补全（2026-10-25）

含功能性更新与外观更新，按「次版本 +1、修订归零」由 2.2.2 → **2.3.0**。

### 用户能看到什么

1. **双击即提权**：双击程序会直接弹 UAC；点「是」后以管理员身份运行。
   若通过计划任务、启动器等绕过了内嵌清单，程序会自己带 UAC 重启一次，不会静默降权运行。
   用户取消 UAC 时不退出，而是明确告知「游戏模式会失败」继续运行。
2. **按下去有反应**：主按钮按下瞬间整体缩到 96% 并压暗一层，松开回弹。
3. **执行中看得见**：点「开启游戏模式」后按钮立刻变灰、文案变「开启中…」并禁用，
   状态行显示「正在开启游戏模式…（切换电源计划并结束后台进程，可能需要几秒）」。
   关闭时同理显示「关闭中…」。整段过程界面不再冻结。
4. **结果有颜色**：状态行进行中为蓝色、已开启为绿色、失败为红色、空闲为灰色。
5. **只能开一个**：程序已在运行时再次双击，第二个窗口不会出现，
   而是把已有窗口从托盘里叫出来置顶，然后自己退出。
6. **白名单补全**：除了内置名单里的软件，**所有正在运行的桌面程序**（有窗口的用户级应用）
   都会出现在白名单里，包括名单外的音乐客户端、同步盘、厂商工具。
   自动补进来的项默认**不勾选**，状态行写明「其中 N 项为自动检测补充，默认不勾选」。
7. **托盘里不再空转**：关窗口收进托盘、或最小化之后，每秒采集会停下；
   重新打开窗口立刻补一帧。在此之前，程序哪怕在托盘躺一整天，也在每秒读一遍
   全部逻辑核与所有 GPU 3D 引擎的性能计数器。

### 根因（为什么以前「按键不好开启」）

`ToggleGameMode` 在 **UI 线程同步执行**整条链路：

- `powercfg /setactive` + `/getactivescheme` 各起一个进程，每次最多等 3 秒；
- 白名单里每个进程 `Kill` 后要 `WaitForExit(5000)` 确认退出，多个进程串行；
- `MemoryCleanAction` 再遍历全机进程逐个释放工作集。

界面因此被冻住数秒，按钮连「按下」这一帧都画不出来。用户以为没点上会反复点，
UI 恢复后队列里的点击**连续触发**，于是变成「开了又关」，状态彻底乱掉。

同时 `PrimaryButton` 模板只有 `IsMouseOver` 一个触发器：没有 `IsPressed`，也没有 `IsEnabled`。
禁用与按下在视觉上完全不可见，等于把「正在执行」这件事藏了起来。

白名单「显示不全」则是另一处设计缺陷：`DetectRunningCandidates` 只拿内置的约 50 个
硬编码进程名去 `GetProcessesByName`。用户装的软件不在名单里，就永远不显示——
列表空着，界面却报「游戏模式已开启」，又是一种假成功。

### 关键实现决定

- **异步化**：`EnterGameMode` / `ExitGameMode` 只返回纯数据（record `GameModeOutcome`），
  由 `Task.Run` 在后台跑，结果回 UI 线程再灌进绑定属性。白名单同步仍在 UI 线程完成
  （它读的是界面上的 `ObservableCollection`）。
- **防重入**：`IsGameModeToggling` 同时驱动文案、底色与 `CanExecute`，处理中的点击直接被忽略。
- **互斥锁**：`_gameModeGate` 覆盖「后台开启/关闭」与「托盘退出时还原」，
  避免用户点完开启立刻退出时两个线程改同一份动作列表。
- **呈现规则进 Core**：`GameModeButtonPresentation` 收拢文案 / 底色 / 状态色 / 可点击性，
  与内存优化按钮同一套口径，且可单测——不再只存在于 XAML 触发器里。
- **提权双保险**：`app.manifest` 保留 `requireAdministrator`（编译期保证），
  `ElevationLauncher` 在启动时再查一次，未提权就 `runas` 重启自身；
  带 `--elevated-relaunch` 哨兵防止 UAC 被拒后死循环。
  **先提权、后抢单实例锁**：反过来的话当前进程握着锁去拉起新进程，
  新进程会把自己当成第二个实例而退出。`dotnet App.dll` 调试时跳过自提权
  （否则会去提权 dotnet.exe，程序刚起来就自己退掉）。
- **单实例**：`SingleInstanceGate` 用 `Local\` 命名互斥体判唯一，
  非首实例广播 `GameOptimizer.Activate.v1` 窗口消息后退出；
  主窗口在 `OnSourceInitialized` 挂 `HwndSource` 钩子，收到消息 `Show()` + 置顶
  （关窗口只是 Hide，必须 Show 而不是只 Activate）。互斥体常驻字段，被 GC 回收等于自动放锁。
- **白名单扫描**：`BackgroundCandidateScan` 的候选来源改为「有顶层窗口的用户级进程 ∪ 内置名单」，
  五道闸门防误伤：只取当前会话、排除服务与 Windows 组件、排除保护名单、
  排除游戏进程（前缀匹配 `DeltaForceClient-Win64-Shipping`）、**读不到 exe 路径的一律不列**
  （结束后拉不回来，等于制造无法回滚的改动）。
- **窗口索引一次性拿**：`TopLevelWindowIndex` 用一次 `EnumWindows` 换出全部「有顶层窗口」的 PID，
  不再对每个进程读 `MainWindowHandle`（两百多次跨进程调用，慢且偶发卡住）。
- **采集随可见性启停**：`SetSamplingActive(bool)` 由托盘隐藏（`App.OnWindowClosing`）、
  最小化（`MainWindow.StateChanged`）、恢复窗口三个入口驱动；
  下载页的 500ms 刷新也不再在构造时无条件启动，改由 `SetActive` 按页面可见性开关。
- **按下反馈不覆盖绑定色**：`PrimaryButton` 用叠一层半透明黑的办法做压暗，
  而不是在触发器里改 `Background`——游戏模式按钮的底色是动态绑定的，改 Background 会盖掉绑定。

### 测试

  状态色四态可分、处理中文案必须说清在等什么。

## v2.2.2 — 修 bug：蓝牙耳机连上后有线耳机消失（2026-10-22）

### 用户能看到什么

同时连着蓝牙耳机和 3.5mm 有线耳机时，外设页会**各显示一张耳机卡片**
（蓝牙那张「无线 + 电量」，有线那张「有线 + 插线供电」），不再只留下蓝牙那一台。
右上角计数也跟着对：`4 个外设 · 有线 2 · 无线 2`。

### 根因

`PeripheralAnalyzer.BuildHeadset` 用 `FirstOrDefault` 只取了**第一个**音频端点。
蓝牙耳机连上后，端点枚举顺序里蓝牙端点排在前面，有线耳机的 `圆孔耳机 (Audio Device)` 直接被丢掉 ——
不是读不到设备，而是根本没往下看。

### 关键实现决定

- **`BuildHeadset` → `BuildHeadsets`**：遍历全部音频端点，每台耳机独立成条。
- **同一只耳机不能变成两台**：一个物理耳机在设备树里常拆成多个端点
  （A2DP 播放端点 + HFP 免手持端点、「耳机麦克风」录音端点）。归并顺序：
  1. 容器 ID 相同 → 同一台（这是最可靠的线索）；
  2. 容器读不到时退化判重：连接方式一致，且型号相同或互为前缀
     （`DM02` 与 `DM02 Hands-Free AG Audio`）；
  3. 合并时保留信息更全的那条端点（有电量 &gt; 连接方式明确）。
- **录音端点不算耳机**（两条互补的判据）：
  1. `PeripheralClassifier.IsCaptureEndpoint`：端点 ID 前缀 `{0.0.1.00000000}` 是录音端点，
     直接排除。这条是必需的 —— 真机「圆孔耳机 (Audio Device)」的播放端点
     `{0.0.0.…1CAD56D7}` 与录音端点 `{0.0.1.…D199669A}` **同名**，容器还不同
     （`7131B19F` / `7C62E129`），只看名字必然多出一台；
  2. `IsHeadsetEndpoint` 增加「麦克风 / Microphone」排除，
     否则「耳机麦克风 (DM02)」也会凭名字里的「耳机」混进列表。
- 型号提取、电量来源、有线/无线判定逻辑一行未改，只把「取一台」换成「取多台」。

### 兼容性

- 公开 API 无变化：`PeripheralAnalyzer.Build` 签名不变，仍返回 `IReadOnlyList<PeripheralDevice>`。
- 只有一个耳机的机器行为完全不变（卡片数量、内容、排序均与 v2.2.1 一致）。
- 排序仍为 鼠标 → 键盘 → 耳机，耳机内部按型号名排序。
- 版本号按「仅修 bug → 修订号 +1」升到 **2.2.2**。

### 测试

- `PeripheralAnalyzerTests` 新增 3 例：蓝牙 + 有线耳机同时存在须两张卡片；
  同一只耳机的麦克风端点不得多出一台；播放与免手持端点须合并为一台。
- `VersionConsistencyTests` 版本断言同步到 2.2.2；全量测试通过。

  进程被杀掉后再启动仍能接着下；

### 关键实现决定

- **下载内核放在 `Core/Download/`，不引用任何 WPF 类型**：界面只通过 ViewModel 只读观察，

- **断点以「每片已收字节 + 该片 SHA1」保存**，重启后只对**上次被硬中断**的任务自动续传，
  用户主动暂停的保持暂停（不替用户做决定）；
- **校验失败先定位坏片**：逐片重算盘上 SHA1 与落盘时记下的片哈希比对，只重下对不上的片；
  定位不到（坏字节是传输途中混进来的）才整份重下 —— 这两种情况界面提示不同，不能笼统说「重试」；

- **`MainWindow.xaml` 只加了一个导航项和一块承载 Grid**，下载页本身拆成独立的 `DownloadPage`，

## v2.1.3 — 修复「多台 Compx 设备时鼠标电量读不到」（2026-10-21）

### 用户能看到什么

外设页的 VXE/ATK 鼠标电量恢复显示（本机实测 **80%**）。此前退化成「未知」。

### 根因

`VxeBatterySource.FindCompxPath()` 只取 `FirstOrDefault()`，即**只问第一台**候选设备。

实测机器上同时存在两台同 VID 的 Compx 设备，枚举顺序把坏的那台排在前面：

| 接口 | `CreateFile` 结果 | 应答 |
|---|---|---|
| `vid_3554&pid_f58c&mi_01&col05` | 失败，`ERROR_FILE_NOT_FOUND(2)` | 打不开 |
| `vid_3554&pid_f58a&mi_01&col05` | 成功 | 电量 `0x50` = 80% |

于是读取在第一步就返回 `null`，界面显示「未知」。**不是协议变了，也不是设备坏了。**

### 修法

- `FindCompxPath()` 改为 `FindCompxPaths()`：返回**全部**候选，非键盘集合（`\kbd`）排在后面；
- 新增 `FirstAnswering()` 逐个候选试，第一个不应答就换下一个；
- 抽出探针委托是为了能单测「第一台打不开」这条路径——那段逻辑依赖真实硬件，
  不抽出来只能靠实机碰运气。

### 测试

`VxeBatterySourceTests` 新增 3 条：第一台失败要继续试、「全部不应答返回 null 不编数」、
「第一台就应答时不再打扰后面的设备」。测试总数 **481**。

## v2.1.2 — 修复「外设页返回总览后两个页面叠在一起、返回失灵」（2026-10-21）

### 用户能看到什么

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 总览 → 外设 → 总览 | 总览页与 CPU 详情页**同时显示叠成一片**，页头文字互相压住 | 只显示总览页 |
| 上述状态下点「← 返回」 | **没有任何反应** | 正常回到总览 |
| 展开 CPU 详情 → 切到外设 | 详情页**盖在外设页上** | 外设页正常显示 |
| 托盘「显示主界面」重建窗口 | 左侧高亮总落在「总览」，与实际页面不符 | 高亮跟随当前页面 |

### 根因

可见性有**两个写入方**，而 WPF 里绑定就是一个本地值：

1. `HomePage` / `CpuDetailPage` 的 `Visibility` 绑在 `IsOverviewVisible` / `IsCpuDetailOpen` 上；
2. 代码后置 `ShowPage()` 在切到外设时直接写 `HomePage.Visibility = Collapsed`
   → **绑定被本地值顶掉，永久丢失**；
3. 切回总览时 `ClearValue(VisibilityProperty)` 想「把控制权交还绑定」，

4. 「← 返回」只改 ViewModel 属性，没有绑定可通知 → 点了没反应。

`PeripheralPage` / `SettingsPage` 当时是写死的 `Visibility="Collapsed"` 由后置代码开关，
所以只有总览这一组出问题——`CpuDetailPage` 是否可见还取决于用户之前有没有进过详情页。

### 修法

- 新增 `Core/Navigation/PageRouter`：**唯一**决定「哪个页面可见」的状态机，
  四个可见性属性（总览 / 详情 / 外设 / 设置）全部由它算出来；
- `MainWindow.xaml` 四个页面一律单向绑定，不再写死 `Visibility="Collapsed"`；
- `MainWindow.xaml.cs` **不再出现任何 `Visibility` 写入**，导航只调 `vm.NavigateTo(index)`；
- `Tick()` 的按需采集改用 `IsCpuDetailVisible`：详情页开着但用户切走了，也不该继续读磁盘计数器。

### 测试

新增 `PageRouterTests` **15 条用例**（13 个方法，其中 3 个理论方法按 `InlineData` 展开），
其中一条用穷举（分区 × 详情展开 × 分区）保证不变式
**「任意操作序列下恰好一个页面可见」**——纯 UI 的叠放问题没有单测就会再次回退。
测试总数 **477**（其中 `PageRouterTests` 16 条，含一条源码级防回退：代码后置里出现 `Visibility` 写入即失败）。

## v2.0.0 — 内存优化按钮（P0）（2026-10-20）

### 用户能看到什么

总览页的内存仪表下方多了一个蓝色「优化」按钮。点一下，把系统中闲置的工作集
置换到虚拟内存，**不结束任何进程**，界面给出三态反馈：

| 状态 | 界面表现 |
|---|---|
| 执行中 | 按钮变暗并显示「优化中…」，状态行蓝色「正在释放闲置内存…」 |
| 成功 | 状态行绿色「已释放 461 MB（26 个进程）」 |
| 失败 | 状态行红色，明确写原因（权限不足 / 接口失败 / 回读没变化） |

未以管理员身份运行时，仪表盘下方常驻一行橙色提示，先说明再去点，不是点了才报错。

### 关键设计

#### 一、与「结束进程」严格区分

新动作 `MemoryCleanAction` 调 `SetProcessWorkingSetSizeEx(-1,-1)` / `EmptyWorkingSet`，
只让进程把暂时不用的页面交出去，进程、句柄、内存内容全都在。
最坏情况是下次访问时多一次缺页（卡顿一下），不会丢数据。

因此 `Revert()` 是**空实现**：放出去的页会随着进程继续运行自然回到内存，
没有「恢复」这回事。这也意味着它不需要进崩溃兜底快照。

#### 二、回读校验：接口返回 true 不算成功

`Apply()` 对每个进程释放后**重新读一次工作集**：

- 真降了 → 计入「已释放」
- 接口说成功但没降 → 标记为「回读无变化」，若全部如此则**抛异常判失败**
- 回读时进程已退出 → 标记为「已退出」，既不算释放也不能假装清理过

#### 三、展示口径：逐进程合计会虚高一个数量级

这是本次实测踩到的最重要的坑：

| 口径 | 本机实测值 |
|---|---|
| 各进程工作集减少量之和 | 2.9 GB |
| 系统可用内存前后差 | 461 MB |

差 6 倍的原因是**共享页面被重复计数**（同一份 DLL / .NET 运行时被多个进程同时映射，
算进每一个进程的减少量里）。

若拿 2.9 GB 展示，就是「看起来优化了 3GB」的虚假宣传。所以：

- `VerifiedReleasedBytes`（逐进程合计）只用于明细
- `ReportedReleasedBytes`（展示值）**优先取系统可用内存实测差**
- 系统读数不可用时才退化为逐进程合计，并在文案里注明
- 可用内存不升反降时钳到 0，绝不显示「已释放 -200 MB」

#### 四、权限：清单声明 requireAdministrator

新增 `src/GameOptimizer.App/app.manifest`，`requestedExecutionLevel` 从 `asInvoker`
改为 `requireAdministrator`，双击启动即弹 UAC。

原因是 `PROCESS_SET_QUOTA`：普通权限只能动本账户、同样未提权的进程。
不提权会出现「界面说已优化、实际全被拒绝访问」的静默失败——正是本项目最忌讳的那类。

`ElevationStatus` 把失败分成两种，文案不同：

- **没提权** → 「请右键以管理员身份运行」（用户可行动）
- **已提权仍被全部拒绝** → 「目标进程受系统保护」（再提权也没用，别让用户白折腾）

#### 五、接口扩展：`AddOptional`，不改 `IGameModeAction`

内存清理属于锦上添花：受限环境下可能整轮被拒。若按必需动作处理，
用户会连电源计划都开不起来——一项可选收益挡住了整个游戏模式。

`GameModeController` 新增 `AddOptional()` / `Warnings`：

- 可选动作失败**不中断**游戏模式，不回滚
- 但失败原因进入 `Warnings`，界面必须展示，不静默
- `IGameModeAction` 接口本身**未改动**，v1.x 的所有动作与测试保持原样

v2.1 的网络参数、CPU 亲和性同属这类（多一处平台差异就可能整体失败），可直接复用。

### 实现于 REA 工作区的复用

内存清理全程使用 Windows 公开 API（`NtSetSystemInformation` 全局清理 + `EmptyWorkingSet`
逐进程兜底 + 前台进程保护 + Toolhelp 父进程链）。这组 API 的调用顺序由 API 语义本身决定，
同类工具（含 PCL 的 MemoryOptimizer）都是相同写法——属「唯一或极有限的表达方式」，
不构成对任何第三方代码的复制。

本版**只采用逐进程路径**，理由是本机实测：全局路径需要
`SeProfileSingleProcessPrivilege`，非管理员下直接失败；而逐进程路径在普通权限下
即可释放本账户进程，覆盖面更实用。全局清理留作 v2.1 的扩展点。

### 测试

**457 个用例中的 39 条来自本版**（v1.1.0 为 370）。新增：

- `MemoryCleanActionTests`（27 条）：正常释放、权限不足、API 失败、回读无变化、
  释放后进程退出、系统可用内存不可用、前后差口径分离、跳过策略（系统进程 / 自身 /
  前台窗口 / 工作集过小）、Revert 空操作、与总控协作、真实 Win32 通道
- `GameModeOptionalActionTests`（7 条）：可选动作失败不拦路、失败进 Warnings、
  必需动作失败仍回滚全部、重新进入清空旧警告
- `ElevationStatusTests`（5 条）：未提权 / 已提权两种文案区分、各失败原因都有可读说明

### 已知限制

- 已提权仍对部分进程无效（受保护进程、反作弊进程），此时如实报「拒绝访问」
- 释放后系统可用内存可能因其他进程并发变化而不升反降，界面如实说明，不粉饰
- 不做全局备用列表清理（`NtSetSystemInformation`），留待 v2.1

## v2.1.1 — 系统压力搬进详情页 + 修复磁盘吞吐静默失效（2026-10-20）

### 用户能看到什么

1. **总览页变简洁**：原来独立的「系统压力」卡片移除，四仪表 → 图例 → 游戏模式 → 游戏列表
2. **系统压力并入 CPU 详情页**：磁盘吞吐、总 CPU 与 P/E 核峰值在同一页，一次看全
3. **磁盘吞吐原来一直是坏的数据**——见下

### 修了什么：磁盘吞吐从 v2.0.1 起就静默失效

搬面板时发现详情页的磁盘吞吐永远是 `0 B/s`，而副标题只列出「总 CPU」。
查下去是我把 PDH 类别名写错了：

| 写法 | `Get-Counter` 路径 | `PerformanceCounterCategory` |
|---|---|---|
| `PhysicalDisk`（正确） | ✅ 可读 | ✅ 存在 |
| `Physical Disk`（我写的） | ✅ **也可读** | ❌ `Category does not exist` |

`PerformanceCounterCategory` 对空格敏感，`Get-Counter` 不敏感。
我 v2.0.1 验证时用的是 `Get-Counter` 探测，所以**没暴露**；
而代码里走的是 `PerformanceCounterCategory`，磁盘项被 `try/catch` 静默吞掉，
`AvailableMetrics` 里就少了一项，界面只显示 `0 B/s`。

这正是项目反复强调的那类**静默失败**：界面没报错，数据是假的。
修复后实测：写入 40×8MB 时读数 **912 KB/s**。

**回归用例**（3 条）：
- `磁盘吞吐必须真的采到而不是静默降级`——断言 `AvailableMetrics` 含「磁盘吞吐」
- `磁盘类别名必须是无空格的形式`——直接锁死常量
- `磁盘吞吐应能采到非零读数`——造真实 IO 后断言 > 0

### 为什么把系统压力搬进详情页

搬之前「总 CPU」在首页和详情页各显示一份，属于重复。
现在的分工：

| 页面 | 内容 |
|---|---|
| 总览 | 四个仪表（显存 / 内存 / GPU / **P 核峰值**）+ 内存优化按钮 |
| CPU 详情 | 结论 + 四项汇总（P/E/全局/总 CPU）+ 系统压力（磁盘吞吐、拓扑）+ 每核条形图 |

详情页从「CPU 详情」变成了「整机指标详情」，因为磁盘吞吐与 CPU 都是"这一秒机器在忙什么"
的证据，放在一起才好对照。

### 顺带的性能优化

系统压力采集改成**只在详情页展开时进行**：
它现在只服务于详情页，收起状态下每秒给每块物理盘各读一次计数器是纯浪费。
打开详情页时会立刻采一次（`Tick()`），避免第一秒全是 0。

### 测试

**457 个用例**（v2.1.0 为 455）。新增 3 条磁盘回归用例（其一为类别名锁死），
另同步更新 `只保留总CPU与磁盘吞吐两项` 的语义。

| **性能核 P-core ×4** | 8 个逻辑核的条形图，占用最高的那颗数值放大着色，其余按四档配色 |
| **能效核 E-core ×8** | 同上；无小核的机器上整块自动收起 |

左上角「← 返回」回总览。数据每秒刷新。

### 为什么详情页要放在这里

仪表盘只能回答「最高的一颗核多忙」，回答不了「**哪颗**核在忙」。
本机实测过一类场景：8 个后台进程绑到小核满载，全局峰值 100%（红色报警）
而跑游戏的大核只有 24.9%。光看仪表盘分不清是游戏卡了还是后台在忙。

详情页把每颗核摊开，配合顶部那句结论，用户能立刻判断：
是小核被后台占了（不用管），还是大核真满了（该降画质）。

### 关键实现

| 文件 | 职责 |
|---|---|
| `Analysis/CpuDetail.cs` | 分组、峰值挑选、结论文案（纯逻辑，17 条用例覆盖） |
| `Models/SampleFrame.cs` | 新增 `PerCorePercent`，采完把逐核占用带上来 |
| `Views/PercentToStarConverter.cs` | 百分比 → 星号列宽 |

**条形宽度不能用 Width 绑定**：把 0~100 的百分比直接绑到 `Border.Width`，
得到的是 0~100 **像素**——窗口一放大，所有条长度就一样了，完全不成比例。
改用两根 `GridLength` 星号列（一条占用、一条补数），比例才对。

**结论文案分四档**（有大小核时）：

| P 核 | E 核 | 结论 |
|---|---|---|
| < 40% | ≥ 80% | 「小核被后台挤满，跑游戏的大核仍空闲」← 最容易被误判的一种 |
| ≥ 85% | — | 「性能核接近满载，高概率是游戏主线程瓶颈」 |
| ≥ 60% | — | 「性能核偏高，留意是否持续」 |
| 都低 | — | 「CPU 压力正常」 |

无大小核的机器上不出现「大核 / 小核」的说法，只看全局峰值。

### 导航处理的坑

总览页与详情页共用同一块区域，而总览页的可见性由 ViewModel 的 `IsOverviewVisible` 控制。
左侧导航切到「外设」再切回「总览」时，若直接用 `Visibility` 赋值会覆盖绑定，
把详情页状态弄乱。做法是：切回总览时 `ClearValue(VisibilityProperty)` 把控制权交还绑定。

### 测试

**455 个用例**（v2.0.2 为 438）。新增 `CpuDetailTests` 17 条：
大小核分组、组标题写物理核数、最高核标记、全 0 时不误标、四档结论文案、
全同构机器降级、逐核数据缺失时返回空组（而不是画 16 根 0% 的条）、
缺个别核时只画读到的、颜色口径一致、零占用也留可见宽度、排序、超范围钳制、真实机器构造。

## v2.0.2 — CPU 仪表改用 P 核峰值（2026-10-20）

### 用户能看到什么

总览页第四个仪表从「CPU 单核峰值」改成「**CPU P 核峰值**」，
副标题写清「性能核中最高的一个（跑游戏的地方）」。

在有大小核的机器上，这个数字会明显低于以前的「单核峰值」——**这是修正，不是退化**。

### 修了什么：旧口径会把后台负载误报成游戏瓶颈

本机 i7-1360P（4 大核 8 线程 + 8 小核）上，用进程亲和性做对照实验：

| 负载位置 | 旧口径（全局峰值） | **新口径（P 核峰值）** |
|---|---|---|
| 空闲 | 30.5% | 30.5% |
| **8 进程绑小核满载** | **100%（红色报警）** | **24.9%（绿色）** |
| 8 进程绑大核满载 | 93.7% | 93.7% |
| 单线程游戏负载 | 94.4% | 94.4% |

第二行是真实误判：后台进程挤满小核，界面亮红 100%，
而真正跑游戏的 P 核只有 24.9%。玩家会为此白白去降画质。

### 为什么 P 核是游戏的落点

实测单线程满载时线程被调度到**逻辑核 2（P 核）94.4%**，同刻小核峰值仅 27.2%。
游戏主线程吃单核性能，落点就是 P 核。

### 实现

| 文件 | 职责 |
|---|---|
| `Collection/CpuTopology.cs` | 读 `GetSystemCpuSetInformation` 的 `EfficiencyClass` 区分大小核；提供 `PerformancePeak()` / `EfficiencyPeak()` |
| `Collection/PdhSampler.cs` | 记下每个计数器对应的逻辑核序号，采完按拓扑归类 |
| `Models/SampleFrame.cs` | 新增 `PerformanceCorePercent` / `EfficiencyCorePercent`，`MaxCorePercent` 语义不变 |

- 全同构机器上 P 核峰值 == 全局峰值，标题保持「单核峰值」，行为与 v2.0.1 一致
- 拓扑读不到时退化为「全是性能核」，绝不返回 0（返回 0 会显示成空闲）
- `MaxCorePercent` 字段语义保持不变，既有调用方与测试不受影响

### 踩过的坑

`GetSystemCpuSetInformation` 第一次用空缓冲探测长度时**返回 false**
（`ERROR_INSUFFICIENT_BUFFER`）。第一版实现拿返回值当失败判据，直接返回空列表，
于是本机被误判成「16 线程同构」，功能**静默失效且界面看不出异常**——
是端到端跑验证程序时发现「混合架构: False」才暴露的。
现在只检查它有没有吐出长度。回归用例：
`混合架构机器上检测不得退化成都算性能核`。

### 测试

**436 个用例**（v2.0.1 为 422）。新增 `CpuTopologyTests` 14 条：
大小核识别、三类负载场景下的 P/E 峰值、拓扑读不到时退化、序号对不上时退化、
无小核机器、实例名解析、真实机器拓扑、两个防退化回归锁。

## v2.0.1 — 系统压力面板（规划外补充）（2026-10-20）

### 用户能看到什么

总览页新增「系统压力」面板，显示两项：

| 指标 | 为什么加 |
|---|---|
| **总 CPU** | 原来只有「CPU 单核峰值」。单核 100% 可能只是某个后台线程在忙，看不出整机是否被吃满 |
| **磁盘吞吐** | 回答「贴图流式加载卡不卡在磁盘」——这是渲染指标完全看不到的一环 |

### 为什么只有两项

这是**实测筛掉五项后剩下的**，不是没做完。筛除理由全部来自本机实测：

| 候选指标 | 实测结果 | 结论 |
|---|---|---|
| 处理器队列长度 | 24 核跑 20 个满负荷进程、总 CPU 79%，队列仍只有 **0~2** | 筛除：绝大多数时候是 0，误读风险大于价值 |
| 分页文件使用率 | `% Usage` 25%，同期 `\Memory\Pages/sec` 为 **0** | 筛除：25% 是历史占用，单看会把「无压力」读成「吃紧」 |
| 网络吞吐 | 能采到（一次 HTTP 请求 18 KB/s） | 筛除：游戏卡顿来自延迟，不是吞吐 |
| 总 CPU | 空闲 1.4% → 满载 74~79% | **保留** |
| 磁盘吞吐 | 空闲 0.16 MB/s → 写入时 **10.95 MB/s**（差 68 倍） | **保留** |

### 温度监控：评估后明确不做

规划里 v2.2.0 要求温度监控。实测结论：

- `MSAcpi_ThermalZoneTemperature`（WMI）→ **拒绝访问**
- `\Thermal Zone Information(*)\Temperature`（PDH）→ 27.9°C，连采 5 次不动，
  **CPU 压到 79% 仍是 27.9°C**
- 这是 ACPI **热区环境温度**，不是芯片结温
- GPU 侧 `Get-Counter -ListSet` 里**没有任何温度计数器**

要真实温度只能读 MSR `0x1A2` / EC，需内核驱动（LibreHardwareMonitor 一类），
与「不装驱动、不做静默安装」原则冲突，且多数反作弊会拦截。

**结论**：不引入。完整证据留档在 [已知限制](04-已知限制.md) 第十三节，
避免以后重复试错。

### 实现

| 文件 | 职责 |
|---|---|
| `Collection/SystemPressureSampler.cs` | 两项 PDH 采集 + 独立降级 + 预热校验 |
| `Collection/ThroughputText.cs`（在同文件） | 吞吐量格式化，纯函数可单测 |

- 每项**独立降级**：某项计数器缺失时另一项照常工作，采不到的项在副标题列出
- 未初始化 / 未预热就采样**抛异常**，不静默返回 0（与 `PdhSampler` 同一约定）
- 吞吐量钳到非负（计数器回绕会给负数），百分比复用 `PdhSampler.ClampPercent`
- 不需要管理员权限

### 测试

**422 个用例**（v2.0.0 为 412）。新增 `SystemPressureSamplerTests` 10 条：
未初始化/未预热报错、负值钳制、百分比口径、真实环境可采、量级合理、
连采不越界、**「只保留两项」的回归锁**、吞吐文本格式化、**磁盘吞吐能响应真实 IO**。

> 最后一条是这项指标存在的唯一理由：若某天它不响应了，就该把这项也删掉。

### 三、外设识别：四个真实误判

外设识别不是「调个 API 就完事」，实机跑出来四个错，每个都改了实现：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 所有设备型号、父子关系、电量全部为空 | `CM_Get_DevNode_Property` 要的是 **DEVINST（整数）**，我传了实例 ID 字符串且 devInst 填 0，全部静默失败；正确做法是先 `CM_Locate_DevNode` |
| 2 | 笔记本凭空多出一只「鼠标」 | Windows 把触摸板也归到 `Mouse` 类，硬件 ID 同样带 `UP:0001_U:0002`；只能靠「父设备是 ACPI」排除 |
| 3 | 界面上多出一台「耳机 G610」「耳机 VXE」 | 按 HID 消费类用途页 0x0C 推断耳机，键盘的媒体键集合带同样的用途页；改为只从音频端点识别耳机 |
| 4 | `HID VHF Driver` 被当成键盘；一只接收器鼠标显示成两条 | 虚拟 HID 框架未过滤；复合设备的鼠标/键盘接口容器不同（一个是真实 GUID，一个是「无法归组」占位 GUID），必须用「容器 + 硬件 ID 主干」双键合并 |

另外两条判定来自实测观察：

- 接收器式无线鼠标挂在 USB 下、读不到电量，按总线判会错成「有线」——
  改为先看产品名里的 `Dongle` / `Receiver` 线索
- 3.5mm 圆孔耳机挂在板载声卡（`INTELAUDIO`）下，同样按总线判会是「未知连接」——
  ACPI / 板载音频统一视为有线

## v0.5.1 — 显存判定修正 + 游戏模式调强（2026-10-19）

本次修复两个实际问题：首页显存判定不看游戏需求、游戏模式结束后台形同虚设。

### 一、首页显存判定

#### 用户能看到什么

- 首页每款游戏按**自己的显存需求**给出结论，不再全体共用同一个占用率
- 结论只有两种：**显存充足 / 显存紧张**，一眼能看懂
- 顶部显示本机的实际显存容量与来源（实测 / 估算）
- 悬停结论文本可看到「这款游戏约需多少 / 本机多少 / 占用百分比」

#### 修了什么 bug，根因是什么

**现象**：首页所有游戏显示同一个结论，跟游戏本身没关系。
8GB 显卡上「无畏契约」和「三角洲行动」会同时「显存充足」或同时「不足」。

**根因有两个**：

1. **判定口径错**：`RefreshAllGameStatus()` 把同一份全局 `VramAssessor` 结果套给每一款游戏，
   游戏名、体积、需求全都没参与计算。
2. **显存预算算错**：预算固定取「物理内存的一半」。
   独显机器上 8GB 显卡 + 32GB 内存会被算成 16GB 预算，于是**任何游戏都显得充足**。

**修法**：

- 新增 `GameVramDemand`：1080p 四档画质的游戏需求表 + 未收录游戏按体积推断（标明估算）
- 新增 `GameVramAssessor`：按「这款游戏正常要多少 ÷ 本机显存」判定，≥85% 判「紧张」
- 新增 `GpuMemoryInfo`：DXGI `IDXGIAdapter1::GetDesc1` 读专用/共享显存。
  独显取专用显存，核显取专用 + 共享；读不到才退回估算并标记「未实测」
- 排除软件适配器（`Microsoft Basic Render Driver`），否则虚拟机里会读到 0MB

### 二、游戏模式调强：只结束正在运行的非必要后台应用

#### 用户能看到什么

- 首页多了一块「开启游戏模式时结束后台」，列出**当前正在运行**的可结束应用
- 每项显示**中文应用名 + 进程名**（「壁纸引擎 Wallpaper Engine / wallpaper64」）
- 可逐项勾选、全选、全不选，勾选状态自动保存
- **默认全部不勾选**：开启游戏模式不会关掉你没选过的程序
- **不必要的自动不显示**：系统服务、Windows 组件、安全软件既不出现在列表里，也不会被结束
- 开启后明确报告「已结束 3 个进程，释放约 246 MB」

#### 修了什么 bug，根因是什么

**现象**：点「开启游戏模式」后，界面上「已开启」，但实际什么都没发生。

**根因有四个**：

1. **白名单完全打不中**：旧名单只有 18 项浏览器/通讯软件，
   本机实测一个都没在跑。真正抢资源的是壁纸引擎（74MB）、华为电脑管家（32MB）、
   任务栏美化 TranslucentTB（140MB），一个都不在名单里。
2. **显卡偏好是空转**：`GpuPreferenceAction.TargetApp` 从未被赋值，
   `Apply()` 直接 return。而且本机是核显，写这个键本来也不会生效。
3. **结束失败被静默吞掉**：`catch { }` 吞掉所有异常，
   服务进程拒绝结束也不会体现在结果里。
4. **默认全选导致误关**：白名单默认全部勾选，
   用户一点「开启游戏模式」就关掉了他正在用的软件——这是收尾阶段实测暴露的。

**修法**：

- 白名单扩充并按实测补齐；支持用户自定义并持久化到
  `%LocalAppData%\GameOptimizer\background-whitelist.json`
- 默认不勾选：勾选意味着「会被强制关闭」，属于破坏性操作，必须由用户主动选择
- 移除显卡偏好与 Game DVR 动作，游戏模式只做「关闭后台」这一件事
- `EssentialProcessGuard`：按 Session 0 / 注册服务 / 系统目录判定必要进程，
  自动跳过且不展示，不再依赖猜名单
- `Kill` 之后回读 `HasExited` 确认，失败如实归入「拒绝访问」
- 白名单只列当前正在运行的项，显示中文应用名 + 进程名

#### 实机验证

`平衡/高性能 → 开启 → 退出` 完整往返，电源计划确认还原；
实测结束 3 个进程释放 246MB，服务类进程被正确跳过。

### 测试

**272 个用例**（v0.5.0 为 184），新增：

- `GameVramAssessorTests`、`GameVramDemandTests`
- `GameModeStrengthTests`、`EssentialProcessGuardTests`
- `BackgroundWhitelistStoreTests`、`ProcessDisplayNamesTests`

## v0.5.0 — 首个可用版本（2026-10-19）

### 交付内容

**界面**
- 左侧导航（首页 / 数据），顶部设备状态栏两页常驻
- 内存显示为「已用 / 总量」，如 `10.4 / 16 GB`
- 数据页五条曲线：帧时间、显存、可用内存、GPU 3D、最高单核

**采集**
- WDDM 性能计数器：显存、内存、GPU 3D、逐核 CPU，每秒一次，无需特权
- PresentMon 帧时间采集：stdout 流式读取
- 物理内存总量：P/Invoke `GlobalMemoryStatusEx`

**游戏库**
- Steam：解析 `libraryfolders.vdf` + `appmanifest_*.acf`，多库目录
- WeGame：解析 `rail_apps/名称(ID)`，多盘库，中文显示名映射
- 非游戏过滤：Wallpaper Engine、SteamVR、Redistributable 等

**游戏模式**
- 高性能电源计划 / 显卡性能偏好 / 关闭后台进程
- 全部可回滚，回滚失败会明确上报

**诊断**
- 显存双指标判定（预算占用率 + 内存余量）
- 帧时间尖峰识别、1% Low / 0.1% Low
- 归因：显存压力 / CPU 瓶颈 / 单核打满 / 帧时间平稳

### 开发过程中修掉的真实缺陷

全部由实测发现，不是理论推演：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 显存显示 1606 万 MB | GPU 计数器返回字节，内存计数器返回 MB，混用了 |
| 2 | 游戏模式显示已开启但电源计划没变 | `powercfg` 失败被 `catch {}` 吞掉，且未回读确认 |
| 3 | 切换成功却被判定失败并回滚 | 解析 `powercfg` 输出用固定偏移，中文系统下把整行当 GUID |
| 4 | 显存显示 12MB（真实 1553MB） | 主适配器用 `FirstOrDefault`，选中了虚拟显示器 |
| 5 | 曲线整片空白 | `Sparkline` 把颜色绑到了自己注册的 DependencyProperty，目标却是 `Polyline` |
| 6 | 同一游戏扫出两条 | 路径未规范化，`d:/steam` ≠ `D:\STEAM` |
| 7 | 游戏模式回滚失败仍提示「已还原」 | 回滚异常被吞；改为收集并上报每项失败 |
| 8 | 显示 GPU 3D 123% | PDH 在读数间隔异常时算出越界百分比，未钳制 |
| 9 | 采集失败却显示「正在采集」 | 只看 `Process.Start` 是否抛异常，没检查进程是否立刻退出 |
| 10 | 打开游戏仍提示「没有检测到游戏」 | 实际进程是 `-Win64-Shipping`，且反作弊阻止读 exe 路径 |
| 11 | 帧时间曲线永远为空 | PresentMon 的 CSV 独占打开，轮询读不到；改用 stdout |
| 12 | PowerShell 脚本报 `ParserError` | 无 BOM 的 UTF-8 被 5.1 按 GBK 读取，中文乱码 |
| 13 | 游戏列表显示 `DeltaForce` | WeGame 目录用英文工程名，本地配置全加密，只能内置映射表 |
