## v2.0.0 — 内存优化按钮（P0）（2026-10-20）

### 用户能看到什么

总览页的内存仪表下方多了一个蓝色「优化」按钮。点一下，把系统中闲置的工作集
置换到虚拟内存，**不结束任何进程**，界面给出三态反馈：

| 状态 | 界面表现 |
|---|---|
| 执行中 | 按钮变暗并显示「优化中…」，状态行蓝色「正在释放闲置内存…」 |
| 成功 | 状态行绿色「已释放 461 MB（26 个进程）」 |
| 失败 | 状态行红色，明确写原因（权限不足 / 接口失败 / 回读没变化） |

未以管理员身份运行时，仪表盘下方常驻一行橙色提示，先说明再去点，不是点了才报错。

### 关键设计

#### 一、与「结束进程」严格区分

新动作 `MemoryCleanAction` 调 `SetProcessWorkingSetSizeEx(-1,-1)` / `EmptyWorkingSet`，
只让进程把暂时不用的页面交出去，进程、句柄、内存内容全都在。
最坏情况是下次访问时多一次缺页（卡顿一下），不会丢数据。

因此 `Revert()` 是**空实现**：放出去的页会随着进程继续运行自然回到内存，
没有「恢复」这回事。这也意味着它不需要进崩溃兜底快照。

#### 二、回读校验：接口返回 true 不算成功

`Apply()` 对每个进程释放后**重新读一次工作集**：

- 真降了 → 计入「已释放」
- 接口说成功但没降 → 标记为「回读无变化」，若全部如此则**抛异常判失败**
- 回读时进程已退出 → 标记为「已退出」，既不算释放也不能假装清理过

#### 三、展示口径：逐进程合计会虚高一个数量级

这是本次实测踩到的最重要的坑：

| 口径 | 本机实测值 |
|---|---|
| 各进程工作集减少量之和 | 2.9 GB |
| 系统可用内存前后差 | 461 MB |

差 6 倍的原因是**共享页面被重复计数**（同一份 DLL / .NET 运行时被多个进程同时映射，
算进每一个进程的减少量里）。

若拿 2.9 GB 展示，就是「看起来优化了 3GB」的虚假宣传。所以：

- `VerifiedReleasedBytes`（逐进程合计）只用于明细
- `ReportedReleasedBytes`（展示值）**优先取系统可用内存实测差**
- 系统读数不可用时才退化为逐进程合计，并在文案里注明
- 可用内存不升反降时钳到 0，绝不显示「已释放 -200 MB」

#### 四、权限：清单声明 requireAdministrator

新增 `src/GameOptimizer.App/app.manifest`，`requestedExecutionLevel` 从 `asInvoker`
改为 `requireAdministrator`，双击启动即弹 UAC。

原因是 `PROCESS_SET_QUOTA`：普通权限只能动本账户、同样未提权的进程。
不提权会出现「界面说已优化、实际全被拒绝访问」的静默失败——正是本项目最忌讳的那类。

`ElevationStatus` 把失败分成两种，文案不同：

- **没提权** → 「请右键以管理员身份运行」（用户可行动）
- **已提权仍被全部拒绝** → 「目标进程受系统保护」（再提权也没用，别让用户白折腾）

#### 五、接口扩展：`AddOptional`，不改 `IGameModeAction`

内存清理属于锦上添花：受限环境下可能整轮被拒。若按必需动作处理，
用户会连电源计划都开不起来——一项可选收益挡住了整个游戏模式。

`GameModeController` 新增 `AddOptional()` / `Warnings`：

- 可选动作失败**不中断**游戏模式，不回滚
- 但失败原因进入 `Warnings`，界面必须展示，不静默
- `IGameModeAction` 接口本身**未改动**，v1.x 的所有动作与测试保持原样

v2.1 的网络参数、CPU 亲和性同属这类（多一处平台差异就可能整体失败），可直接复用。

### 实现于 REA 工作区的复用

内存清理的 Win32 序列来自「逆向REA」工作区已完成的 PCL2 `MemoryOptimizer` 实现
（`NtSetSystemInformation` 全局清理 + 逐进程兜底 + 前台进程保护 + Toolhelp 父进程链）。

本版**只采用逐进程路径**，理由是本机实测：全局路径需要
`SeProfileSingleProcessPrivilege`，非管理员下直接失败；而逐进程路径在普通权限下
即可释放本账户进程，覆盖面更实用。全局清理留作 v2.1 的扩展点。

### 测试

**406 个用例**（v1.1.0 为 370）。新增：

- `MemoryCleanActionTests`（27 条）：正常释放、权限不足、API 失败、回读无变化、
  释放后进程退出、系统可用内存不可用、前后差口径分离、跳过策略（系统进程 / 自身 /
  前台窗口 / 工作集过小）、Revert 空操作、与总控协作、真实 Win32 通道
- `GameModeOptionalActionTests`（7 条）：可选动作失败不拦路、失败进 Warnings、
  必需动作失败仍回滚全部、重新进入清空旧警告
- `ElevationStatusTests`（5 条）：未提权 / 已提权两种文案区分、各失败原因都有可读说明

### 已知限制

- 已提权仍对部分进程无效（受保护进程、反作弊进程），此时如实报「拒绝访问」
- 释放后系统可用内存可能因其他进程并发变化而不升反降，界面如实说明，不粉饰
- 不做全局备用列表清理（`NtSetSystemInformation`），留待 v2.1

## v2.0.1 — 系统压力面板（规划外补充）（2026-10-20）

### 用户能看到什么

总览页新增「系统压力」面板，显示两项：

| 指标 | 为什么加 |
|---|---|
| **总 CPU** | 原来只有「CPU 单核峰值」。单核 100% 可能只是某个后台线程在忙，看不出整机是否被吃满 |
| **磁盘吞吐** | 回答「贴图流式加载卡不卡在磁盘」——这是渲染指标完全看不到的一环 |

### 为什么只有两项

这是**实测筛掉五项后剩下的**，不是没做完。筛除理由全部来自本机实测：

| 候选指标 | 实测结果 | 结论 |
|---|---|---|
| 处理器队列长度 | 24 核跑 20 个满负荷进程、总 CPU 79%，队列仍只有 **0~2** | 筛除：绝大多数时候是 0，误读风险大于价值 |
| 分页文件使用率 | `% Usage` 25%，同期 `\Memory\Pages/sec` 为 **0** | 筛除：25% 是历史占用，单看会把「无压力」读成「吃紧」 |
| 网络吞吐 | 能采到（一次 HTTP 请求 18 KB/s） | 筛除：游戏卡顿来自延迟，不是吞吐 |
| 总 CPU | 空闲 1.4% → 满载 74~79% | **保留** |
| 磁盘吞吐 | 空闲 0.16 MB/s → 写入时 **10.95 MB/s**（差 68 倍） | **保留** |

### 温度监控：评估后明确不做

规划里 v2.2.0 要求温度监控。实测结论：

- `MSAcpi_ThermalZoneTemperature`（WMI）→ **拒绝访问**
- `\Thermal Zone Information(*)\Temperature`（PDH）→ 27.9°C，连采 5 次不动，
  **CPU 压到 79% 仍是 27.9°C**
- 这是 ACPI **热区环境温度**，不是芯片结温
- GPU 侧 `Get-Counter -ListSet` 里**没有任何温度计数器**

要真实温度只能读 MSR `0x1A2` / EC，需内核驱动（LibreHardwareMonitor 一类），
与「不装驱动、不做静默安装」原则冲突，且多数反作弊会拦截。

**结论**：不引入。完整证据留档在 [已知限制](04-已知限制.md) 第十三节，
避免以后重复试错。

### 实现

| 文件 | 职责 |
|---|---|
| `Collection/SystemPressureSampler.cs` | 两项 PDH 采集 + 独立降级 + 预热校验 |
| `Collection/ThroughputText.cs`（在同文件） | 吞吐量格式化，纯函数可单测 |

- 每项**独立降级**：某项计数器缺失时另一项照常工作，采不到的项在副标题列出
- 未初始化 / 未预热就采样**抛异常**，不静默返回 0（与 `PdhSampler` 同一约定）
- 吞吐量钳到非负（计数器回绕会给负数），百分比复用 `PdhSampler.ClampPercent`
- 不需要管理员权限

### 测试

**422 个用例**（v2.0.0 为 412）。新增 `SystemPressureSamplerTests` 10 条：
未初始化/未预热报错、负值钳制、百分比口径、真实环境可采、量级合理、
连采不越界、**「只保留两项」的回归锁**、吞吐文本格式化、**磁盘吞吐能响应真实 IO**。

> 最后一条是这项指标存在的唯一理由：若某天它不响应了，就该把这项也删掉。

## v1.1.0 — VXE/ATK 鼠标实时电量（2026-10-20）

### 用户能看到什么

外设页的 VXE / ATK（Compx 方案）无线鼠标不再显示「电量未知」，
而是**实时读到真实剩余电量**（本机 VXE R1 实测读到 65%）。

### 协议来源与验证

连接「逆向REA」工作区已完成的任务：hub.atk.pro 前端 WebHID 驱动逆向，
提取 Compx 方案电量读取的私有 HID 协议，再在本机真实鼠标上实测确认：

| 项 | 值 |
|---|---|
| 设备匹配 | FF02 厂商集合（`hid#vid_3554&pid_f58a&mi_01&col05`，usagePage=0xFF02 usage=2） |
| 包格式 | 16 字节包 + 报告 ID 8 前置；[0]commandId [5]batteryLevel [6]charge [7-8]voltage [15]checkSum |
| 电量查询 | commandId=4（GetBatteryLevel） |
| 校验和 | 字节15 = 85 − (sum(报告ID8 + 前15字节) & 255) |
| 交互时序 | SetOutputReport → WriteFile 触发 → ReadFile 取 17 字节响应（实测顺序，GetInputReport 只回零不可用） |
| 实测抓包 | 响应 `08 04 00 00 00 02 41 00 0F 83 00 00 00 00 00 00 74` → 电量 0x41=65%，校验和 0x74 ✓ |

实现：`VxeBatterySource`（Core/Peripherals），纯函数（组包/解析/VID 匹配）可单测；
`PeripheralScanner` 扫描后实时读取，把电量填进对应鼠标卡片，读不到保持「未知」。

### 测试

**347 个用例**（v1.0.2 为 337）。新增 `VxeBatterySourceTests` 10 条：
实测抓包字节锁死、65% 解析、充电状态、校验和错误/命令码不匹配/电量越界拒收、
VID 提取与匹配、真实设备读取。

## v1.0.2 — 托盘常驻 + 卸载残留误报修复（2026-10-20）

### 用户能看到什么

1. **托盘运行（补最初要求）**：点窗口关闭按钮不再退出程序，而是收进系统托盘继续后台采集；
   托盘图标双击或右键「显示主界面」恢复窗口，右键「退出」才真正结束进程
   （退出前自动还原游戏模式与恢复被结束的进程）
2. **已卸载的游戏不再出现在游戏库**：ChainedTogether 卸载后本机只剩一个 53 字节的
   云存档占位文件（`steam_autocloud.vdf`），旧版兜底扫描仍把它当成游戏入库。
   现在兜底扫描要求目录里必须还有游戏主程序（exe），卸载残留的空壳目录自动跳过

### 关键设计

- **托盘实现**：`App.ShutdownMode = OnExplicitShutdown` + `NotifyIcon`
  （WinForms 与 WPF 共存，csproj 开 `UseWindowsForms`）。窗口 `Closing` 事件里
  `e.Cancel = true` 并 `Hide()`；只有托盘「退出」置 `_reallyExit` 才放行真正关闭，
  保证退出路径必然走 `OnExit → _vm.Shutdown()` 还原游戏模式
- **托盘图标**：exe 没有嵌入 .ico 资源，运行时用 GDI+ 自绘「优」字图标；
  `GetHicon` 后 `Clone()` 再销毁句柄，避免 Dispose 图标时释放掉还在用的句柄
- **卸载残留判定**：`BuildFallbackEntry` 先 `FindMainExecutable`，
  目录里没有 exe 就返回 null 不入库。appmanifest 路径（`ParseManifest`）不受影响，
  正常安装的游戏照常入库

### 测试

**337 个用例**（v1.0.1 为 334）。新增 `SteamLibraryScannerTests` 三条：
卸载残留空壳目录排除、带主程序的移库目录保留、真实扫描不含 ChainedTogether。

## v1.0.1 — 五项微调（2026-10-20）

### 用户能看到什么

1. **外设页不再显示笔记本自带键盘**：板载键盘（父设备挂在 ACPI 下的 Keyboard 类设备）被过滤，
   外接键盘（USB / 蓝牙）照常显示
2. **右上角页签删除**：页面切换只保留左侧导航，不再有两套切换入口
3. **白名单收进设置面板**：原「开启游戏模式时结束后台」整块卡片折叠，
   「开启游戏模式」按钮旁新增**白名单设置**按键，点击展开带**应用图标 + 应用名称**的勾选面板
4. **NARAKA: BLADEPOINT 显示为「永劫无间」**：新增 Steam 显示名映射表；
   游戏库扫描补齐——Steam 对没有 appmanifest 的 `steamapps\common` 目录兜底入库
   （原工具的做法，实测本机 ChainedTogether 移库后只剩目录没有 acf），
   WeGame 增加全盘根目录探测
5. **开启游戏模式后按钮变红色「关闭游戏模式」**；关闭时**自动恢复被结束的进程**
   （按结束前记下的可执行文件路径重新拉起；读不到路径的进程不自动恢复并如实说明）

### 关键设计

- **内置键盘判定**放在 `PeripheralAnalyzer.IsBuiltInKeyboard`：只对「父设备是 ACPI」的键盘生效。
  外接键盘挂在 USB / BTHENUM 下永远不会误伤；外接 PS/2 键盘挂在 PCI i8042 控制器下也不受影响
- **进程恢复**放在 `EndProcessAction`：`Apply()` 结束时在 `KilledProcess` 之外额外记录
  `RestoredProcess`（进程名 + 可执行文件路径）；`Revert()` 按原路径 `Process.Start` 拉起，
  失败的恢复记录通过 `FailedRestores` 上报到界面状态行——不静默假装恢复了
- **图标提取**：App 层 `AppIconCache` 从进程 exe 提取图标（与任务管理器同源），
  提取失败时界面退化为「首字符色块」，绝不显示空白
- 游戏模式按钮颜色由 ViewModel 的 `GameModeButtonHex` 驱动（开启 `#FF453A` 红 / 关闭 `#4C8DFF` 蓝），
  不写死在 XAML 触发器里

### 测试

**334 个用例**（v1.0.0 为 317）。新增 `PeripheralAnalyzerTests` 内置键盘过滤用例、
`SteamDisplayNamesTests`、`ProcessRestoreTests`、`NonGameFilterTests` 目录名过滤用例；
既有 `SteamLibraryScannerTests` 与 `VersionConsistencyTests` 同步更新。

## v1.0.0 — 百分比仪表盘 + 外设页 + 深色窗口（2026-10-19）

本次是外观与页面结构的大改：首页改成仪表盘，「数据」页整体换成「外设」页，
窗口去掉系统白框，整体风格对齐参考图（近黑背景 + 深灰卡片 + 小圆角）。

### 一、首页：百分比仪表盘

#### 用户能看到什么

- 显存、内存、GPU 3D、CPU 单核峰值四项，全部改成环形仪表盘
- 颜色按占用率分四档：**0~30% 绿 · 31~60% 蓝 · 61~80% 橙 · 81~100% 红**
- 仪表下方给出绝对数字（`1565 / 8182 MB`、`11.5 / 16 GB`）
- 底部有一行颜色图例，用户不用猜颜色代表什么

#### 关键设计

- 分档规则放在 Core 的 `OccupancyPalette`，不在 XAML 触发器里：
  这样能单测，也不会出现「这里绿、那里红」的两套口径
- 角度计算放在 `GaugeGeometry`，同样有单测。**画在 WPF 里的东西出错时肉眼极难发现**
  （弧长算成 0 就整圈消失，算成 359.99 就留一条缝），必须锁死
- 100% 强制扫满整圈：浮点乘除可能算出 359.99999，圆环上会留一条肉眼可见的缝
- 越界读数先钳制：PDH 在读数间隔异常时给过 123%，界面上不会出现越界百分比

### 二、「数据」页 → 「外设」页

#### 用户能看到什么

- 左侧导航与顶部页签里的「数据」变成「外设」
- 外设页分鼠标 / 键盘 / 耳机三类，每台一张卡片：
  - 具体型号（`G610`、`VXE NordicMouse 1K Dongle`）
  - 厂商（`Logitech`、`Compx`）
  - 剩余电量环形图
  - 有线连接显示「有线」，模块主题色为蓝色
- 卡片左下角说明这个结论的来源（`USB / 板载接口直连`、`厂商私有协议，Windows 读不到电量`）
- 「重新扫描」按钮：插拔设备后手动刷新

#### 删掉了什么

按要求删除数据页及其全部依赖，但保证工具其他部分照常运行：

| 删除 | 原因 |
|---|---|
| `FrameTimeSource` | PresentMon 帧采集，数据页专用 |
| `FrameTimeAnalyzer` | 帧时间统计，只服务数据页 |
| `DiagnosisEngine` + `DiagnosisFinding` | 卡顿归因，输入只有帧时间 |
| `ChartGeometry` + `Sparkline` | 自绘曲线，数据页专用 |
| `SampleFrame.FrameTimeMs` | 字段本身失去意义 |

删除后 `PdhSampler.Sample()` 不再接收帧时间参数；首页显存判定、内存显示、
游戏模式、白名单等功能完全不受影响（已用 317 个用例验证）。

外部脚本 `tools/verify-frametime.ps1` 保留：它用于单独验证 PresentMon 的 ETW 链路，
不依赖程序内部代码，删掉反而会丢失排障手段。

### 三、外设识别：四个真实误判

外设识别不是「调个 API 就完事」，实机跑出来四个错，每个都改了实现：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 所有设备型号、父子关系、电量全部为空 | `CM_Get_DevNode_Property` 要的是 **DEVINST（整数）**，我传了实例 ID 字符串且 devInst 填 0，全部静默失败；正确做法是先 `CM_Locate_DevNode` |
| 2 | 笔记本凭空多出一只「鼠标」 | Windows 把触摸板也归到 `Mouse` 类，硬件 ID 同样带 `UP:0001_U:0002`；只能靠「父设备是 ACPI」排除 |
| 3 | 界面上多出一台「耳机 G610」「耳机 VXE」 | 按 HID 消费类用途页 0x0C 推断耳机，键盘的媒体键集合带同样的用途页；改为只从音频端点识别耳机 |
| 4 | `HID VHF Driver` 被当成键盘；一只接收器鼠标显示成两条 | 虚拟 HID 框架未过滤；复合设备的鼠标/键盘接口容器不同（一个是真实 GUID，一个是「无法归组」占位 GUID），必须用「容器 + 硬件 ID 主干」双键合并 |

- 接收器式无线鼠标挂在 USB 下、读不到电量，按总线判会错成「有线」——

  ACPI / 板载音频统一视为有线

## v0.5.1 — 显存判定修正 + 游戏模式调强（2026-10-19）

本次修复两个实际问题：首页显存判定不看游戏需求、游戏模式结束后台形同虚设。

### 一、首页显存判定

#### 用户能看到什么

- 首页每款游戏按**自己的显存需求**给出结论，不再全体共用同一个占用率
- 结论只有两种：**显存充足 / 显存紧张**，一眼能看懂
- 顶部显示本机的实际显存容量与来源（实测 / 估算）
- 悬停结论文本可看到「这款游戏约需多少 / 本机多少 / 占用百分比」

#### 修了什么 bug，根因是什么

**现象**：首页所有游戏显示同一个结论，跟游戏本身没关系。
8GB 显卡上「无畏契约」和「三角洲行动」会同时「显存充足」或同时「不足」。

**根因有两个**：

1. **判定口径错**：`RefreshAllGameStatus()` 把同一份全局 `VramAssessor` 结果套给每一款游戏，
   游戏名、体积、需求全都没参与计算。
2. **显存预算算错**：预算固定取「物理内存的一半」。
   独显机器上 8GB 显卡 + 32GB 内存会被算成 16GB 预算，于是**任何游戏都显得充足**。

**修法**：

- 新增 `GameVramDemand`：1080p 四档画质的游戏需求表 + 未收录游戏按体积推断（标明估算）
- 新增 `GameVramAssessor`：按「这款游戏正常要多少 ÷ 本机显存」判定，≥85% 判「紧张」
- 新增 `GpuMemoryInfo`：DXGI `IDXGIAdapter1::GetDesc1` 读专用/共享显存。
  独显取专用显存，核显取专用 + 共享；读不到才退回估算并标记「未实测」
- 排除软件适配器（`Microsoft Basic Render Driver`），否则虚拟机里会读到 0MB

### 二、游戏模式调强：只结束正在运行的非必要后台应用

#### 用户能看到什么

- 首页多了一块「开启游戏模式时结束后台」，列出**当前正在运行**的可结束应用
- 每项显示**中文应用名 + 进程名**（「壁纸引擎 Wallpaper Engine / wallpaper64」）
- 可逐项勾选、全选、全不选，勾选状态自动保存
- **默认全部不勾选**：开启游戏模式不会关掉你没选过的程序
- **不必要的自动不显示**：系统服务、Windows 组件、安全软件既不出现在列表里，也不会被结束
- 开启后明确报告「已结束 3 个进程，释放约 246 MB」

#### 修了什么 bug，根因是什么

**现象**：点「开启游戏模式」后，界面上「已开启」，但实际什么都没发生。

**根因有四个**：

1. **白名单完全打不中**：旧名单只有 18 项浏览器/通讯软件，
   本机实测一个都没在跑。真正抢资源的是壁纸引擎（74MB）、华为电脑管家（32MB）、
   任务栏美化 TranslucentTB（140MB），一个都不在名单里。
2. **显卡偏好是空转**：`GpuPreferenceAction.TargetApp` 从未被赋值，
   `Apply()` 直接 return。而且本机是核显，写这个键本来也不会生效。
3. **结束失败被静默吞掉**：`catch { }` 吞掉所有异常，
   服务进程拒绝结束也不会体现在结果里。
4. **默认全选导致误关**：白名单默认全部勾选，
   用户一点「开启游戏模式」就关掉了他正在用的软件——这是收尾阶段实测暴露的。

**修法**：

- 白名单扩充并按实测补齐；支持用户自定义并持久化到
  `%LocalAppData%\GameOptimizer\background-whitelist.json`
- 默认不勾选：勾选意味着「会被强制关闭」，属于破坏性操作，必须由用户主动选择
- 移除显卡偏好与 Game DVR 动作，游戏模式只做「关闭后台」这一件事
- `EssentialProcessGuard`：按 Session 0 / 注册服务 / 系统目录判定必要进程，
  自动跳过且不展示，不再依赖猜名单
- `Kill` 之后回读 `HasExited` 确认，失败如实归入「拒绝访问」
- 白名单只列当前正在运行的项，显示中文应用名 + 进程名

#### 实机验证

`平衡/高性能 → 开启 → 退出` 完整往返，电源计划确认还原；
实测结束 3 个进程释放 246MB，服务类进程被正确跳过。

### 测试

**272 个用例**（v0.5.0 为 184），新增：

- `GameVramAssessorTests`、`GameVramDemandTests`
- `GameModeStrengthTests`、`EssentialProcessGuardTests`
- `BackgroundWhitelistStoreTests`、`ProcessDisplayNamesTests`

## v0.5.0 — 首个可用版本（2026-10-19）

### 交付内容

**界面**
- 左侧导航（首页 / 数据），顶部设备状态栏两页常驻
- 内存显示为「已用 / 总量」，如 `10.4 / 16 GB`
- 数据页五条曲线：帧时间、显存、可用内存、GPU 3D、最高单核

**采集**
- WDDM 性能计数器：显存、内存、GPU 3D、逐核 CPU，每秒一次，无需特权
- PresentMon 帧时间采集：stdout 流式读取
- 物理内存总量：P/Invoke `GlobalMemoryStatusEx`

**游戏库**
- Steam：解析 `libraryfolders.vdf` + `appmanifest_*.acf`，多库目录
- WeGame：解析 `rail_apps/名称(ID)`，多盘库，中文显示名映射
- 非游戏过滤：Wallpaper Engine、SteamVR、Redistributable 等

**游戏模式**
- 高性能电源计划 / 显卡性能偏好 / 关闭后台进程
- 全部可回滚，回滚失败会明确上报

**诊断**
- 显存双指标判定（预算占用率 + 内存余量）
- 帧时间尖峰识别、1% Low / 0.1% Low
- 归因：显存压力 / CPU 瓶颈 / 单核打满 / 帧时间平稳

### 开发过程中修掉的真实缺陷

全部由实测发现，不是理论推演：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 显存显示 1606 万 MB | GPU 计数器返回字节，内存计数器返回 MB，混用了 |
| 2 | 游戏模式显示已开启但电源计划没变 | `powercfg` 失败被 `catch {}` 吞掉，且未回读确认 |
| 3 | 切换成功却被判定失败并回滚 | 解析 `powercfg` 输出用固定偏移，中文系统下把整行当 GUID |
| 4 | 显存显示 12MB（真实 1553MB） | 主适配器用 `FirstOrDefault`，选中了虚拟显示器 |
| 5 | 曲线整片空白 | `Sparkline` 把颜色绑到了自己注册的 DependencyProperty，目标却是 `Polyline` |
| 6 | 同一游戏扫出两条 | 路径未规范化，`d:/steam` ≠ `D:\STEAM` |
| 7 | 游戏模式回滚失败仍提示「已还原」 | 回滚异常被吞；改为收集并上报每项失败 |
| 8 | 显示 GPU 3D 123% | PDH 在读数间隔异常时算出越界百分比，未钳制 |
| 9 | 采集失败却显示「正在采集」 | 只看 `Process.Start` 是否抛异常，没检查进程是否立刻退出 |
| 10 | 打开游戏仍提示「没有检测到游戏」 | 实际进程是 `-Win64-Shipping`，且反作弊阻止读 exe 路径 |
| 11 | 帧时间曲线永远为空 | PresentMon 的 CSV 独占打开，轮询读不到；改用 stdout |
| 12 | PowerShell 脚本报 `ParserError` | 无 BOM 的 UTF-8 被 5.1 按 GBK 读取，中文乱码 |
| 13 | 游戏列表显示 `DeltaForce` | WeGame 目录用英文工程名，本地配置全加密，只能内置映射表 |
