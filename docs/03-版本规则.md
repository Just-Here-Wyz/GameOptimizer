# 版本规则

## 编号约定（按规则自动推进）

| 变更类型 | 版本变化 | 示例 |
|---|---|---|
| **外观 / 功能性更新** | 次版本号 +1，修订号归零 | v2.4.1 → **v2.5.0** |
| **仅修 bug** | 修订号 +1 | v2.4.1 → **v2.4.2** → v2.4.3 … |
| 大版本（用户明确要求） | 主版本号 +1，其余归零 | v2.5.0 → **v3.0.0** |

**版本号不再由人手工维护，按上表规则用脚本推进**：

```powershell
pwsh -File tools/bump-version.ps1 -Kind feature   # 功能性更新（默认值）
pwsh -File tools/bump-version.ps1 -Kind fix       # 仅修 bug
pwsh -File tools/bump-version.ps1 -Kind major     # 大版本
pwsh -File tools/bump-version.ps1 -Set 2.5.0      # 补录 / 回退到指定版本
pwsh -File tools/bump-version.ps1 -Kind fix -DryRun   # 只看会改什么
```

一次改动里既有新功能又有 bug 修复时取**较大者**（功能更新优先，修订号归零）。

## 版本号在哪里改

只跑脚本，不要手工改版本号——它在七个地方出现，漏一处就会出现「代码 2.5.0、文档还写 2.4.1」：

| 位置 | 内容 |
|---|---|
| `Directory.Build.props` | `<Version>` / `<AssemblyVersion>` / `<FileVersion>`（唯一真源，三个项目继承） |
| `tests/…/VersionConsistencyTests.cs` | 「当前版本应为X_Y_Z」硬断言（方法名 + 三个数字） |
| `docs/02-功能清单.md` | 标题 |
| `docs/04-已知限制.md` | 标题 |
| `docs/03-版本规则.md` | 本文「当前版本」一行 |
| `docs/README.md` | 首行「当前版本」 |
| `README.md` | 徽标行、版本状态行 |

`VersionConsistencyTests` 里另有一条用例直接把 `Directory.Build.props` 与程序集版本、
两份文档标题的版本号比对，脚本漏改任何一处都会当场变红。

**脚本不猜的两处**（需要人写内容）：

- `docs/06-变更记录.md` 的小节标题（`## vX.Y.Z — 一句话说明`）
- `docs/README.md` 版本历史表补一行

**README 的下载链接与附件表不跟着版本号走**：只要还没打包上传，链接必须继续指向
最近发布的那一版；换了会变成死链。`最近发布` 那几个字由脚本按 Git tag 自动填。

## 发布流程

每次更新按这个顺序做，确保可追溯：

1. **改代码**
2. **补测试**，`dotnet test` 全绿
3. **跑 `tools/bump-version.ps1`**（按规则推进版本号，顺带同步文档与测试里的断言）
4. **补 `docs/06` 小节标题与 `docs/README` 版本历史表**（脚本不猜内容）
5. **提交**，提交信息用中文，格式：

```
fix: 简短说明      ← 修 bug
feat: 简短说明     ← 新功能
docs: 简短说明     ← 仅文档
refactor: 简短说明 ← 重构
```

6. **打标签并推送**：

```powershell
git tag -a v2.5.2 -m "v2.5.2"
git push origin v2.5.2
```

7. **等流水线出包**（不用手工打包上传）：`v*` tag 一推，`.github/workflows/release.yml`
   就在 `windows-latest` 上跑完整套——校验 tag 与 `Directory.Build.props` 版本一致 →
   `installer/build-installer.ps1`（构建 + 全量用例 + 单文件发布 + ISCC 编译安装包）→
   创建或复用 Release → 上传 exe、Setup、本版 `SHA256SUMS.txt`。

   两个容易踩的点：

   - **tag 名必须等于 `v` + 源码版本**。不一致时流水线在第三步就 `throw`，不会打出一个
     「文件名写 2.5.3、程序里还是 2.5.2」的包。所以顺序永远是「先 bump 版本号、提交，再打 tag」。
   - **附件会被 `--clobber` 覆盖**。同版本重跑是安全的，但手工往 Release 上放的东西
     （手打的发布说明除外）会被同名附件顶掉。

   失败时不用翻几千行日志：失败用例名会直接写进 Actions 摘要，产物与 trx 另有 artifact 留档 7 天。

## 仓库为什么这样设

`main` 开了分支保护：**禁止强推和删除**（覆盖掉的 commit 在远端找不回来），协作者的 PR
必须 `构建与测试（Windows x64）` 绿了才能合。管理员保留了绕过通道——这条检查名是写死在
保护规则里的，万一哪天 job 改名、检查永远等不到，还能手动推一次把规则改回来。

`Wiki` 与 `Projects` 是关闭的：知识只放 `docs/` 一份，避免同一个问题在三个地方各写一半。

## 变更记录怎么写

在 `docs/06-变更记录.md` 顶部追加一节，至少写清楚：

- **用户能看到什么变化**（不是技术实现）
- **修了什么 bug，根因是什么**（避免以后重复踩坑）
- **测试数量变化**
