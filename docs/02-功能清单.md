# 功能清单（v2.4.0）

## 一、总览页

| 功能 | 状态 | 说明 |
|---|---|---|
| 百分比仪表盘 | ✅ | 显存、内存、GPU 3D、CPU 四项，环形显示占用百分比 |
| **CPU 仪表取整机总占用** | ✅ | 主指标换成**真实总体占用率**（PDH `\Processor(_Total)\% Processor Time`），不是把 P 核峰值改个名字。P 核峰值仍留在高级详情里做单核判断。读不到读数时环内显示「未知」，不画 0%（0% 是「测到了空闲」，不是「没测到」） |
| **点 CPU 卡片进诊断页** | ✅ | 点仪表与文字区域（Border + MouseBinding）进入 CPU 页的**诊断**视图；下方「CPU 优化」按钮走**独立的快速优化流程**。两者是并列控件而非嵌套按钮，一次点击只跑一条路径 |
| 同构机器行为不变 | ✅ | 无大小核的机器上 P 核峰值 == 全局峰值，标题仍为「CPU 单核峰值」，详情页不出现「大核 / 小核」说法 |
| 四档配色 | ✅ | 0~30% 绿、31~60% 蓝、61~80% 橙、81~100% 红；口径在 `OccupancyPalette`，有单测锁死 |
| 超范围读数钳制 | ✅ | PDH 在读数间隔异常时给过 123%，界面上不会出现越界百分比 |
| **内存优化按钮** | ✅ | 内存仪表下方「优化」按钮，释放闲置工作集；三态可见（执行中 / 成功 / 失败）；**不结束任何进程** |
| 内存优化结果如实上报 | ✅ | 成功显示「已释放 461 MB（26 个进程）」；失败写清原因（权限不足 / 接口失败 / 回读无变化） |
| **系统压力并入详情页** | ✅ | v2.1.1 起从总览页移入 CPU 页；v2.3.x 起随逐核数据一起落在**高级详情**视图，磁盘吞吐与 P/E/全局峰值同页对照，总 CPU 不再重复出现（诊断视图已有） |
| 系统压力独立降级 | ✅ | 某项计数器缺失时另一项照常工作，采不到的项在副标题列出，不显示 0 冒充读数 |
| 游戏库自动扫描 | ✅ | 同时扫描 Steam 与 WeGame，启动时自动执行，可手动「重新扫描」 |
| 平台分组统计 | ✅ | 显示「已扫描到 N 款游戏（WeGame 2 款，Steam 1 款）」 |
| 非游戏过滤 | ✅ | Wallpaper Engine、SteamVR、各类 Redistributable 不入库 |
| 显存是否充足 | ✅ | **按每款游戏自己的正常需求（1080p 高画质）对比本机实时剩余显存**，每秒重算；结论只有「显存充足 / 显存紧张」两种；悬停可看需求、剩余与占比 |
| 剩余显存口径 | ✅ | 剩余 = 显存容量 − 当前占用（PDH `GPU Adapter Memory\Total Committed`）。总容量再大，被别的程序占满时同样判「紧张」 |

> 内存优化默认保护：系统必要进程（Session 0 / 注册服务 / 系统目录）、本程序自身、
> 当前前台窗口进程、工作集小于 16MB 的进程。前台进程被清会让用户明显感到卡顿。

> **系统压力只做两项，是实测筛出来的结果**：处理器队列长度（24 核压到 79% CPU 仍为 0~2）、
> 分页文件使用率（静态 25% 而同期 `Pages/sec` 为 0）、网络吞吐（与游戏延迟无关）三项
> 实测价值不足，已筛除。**温度监控明确不做**（ACPI 只能给恒定的环境温度，真实核心温度需内核驱动）。
> 实测证据见 [已知限制](04-已知限制.md) 第十三、十四节。

## 二、CPU 页（v2.4.0 新增）

页面顶部有横向二级导航：**CPU 诊断**（默认）/ **高级详情**。二级视图只决定页内显示哪一块，
不影响左侧主导航；状态由 `PageRouter.CpuTab` 单一真源决定，XAML 只绑定可见性。

### 2.1 CPU 诊断

| 功能 | 状态 | 说明 |
|---|---|---|
| 当前占用 | ✅ | 整机总占用率，与首页仪表**同一个计数器**、同一秒只读一次。读不到写「未知」 |
| 30 秒平均 | ✅ | 取最近 30 秒**有效帧**平均；没有有效帧时写「30 秒平均未知」，不用 0 补 |
| 趋势图 | ✅ | 自绘折线（`CpuTrendChart`），横轴换算在 Core 的 `CpuTrendGeometry`（有单测）；只画有效帧，缺帧留空而不是画到 0 |
| 负载判定 | ✅ | ≥80% 连续 10 秒 → 持续高负载；≥60% 连续 10 秒 → 持续偏高；不足 10 秒 → 「采样中」，不下结论 |
| 单核判定 | ✅ | 单核瞬时 ≥80% 仅记录；单核 ≥90% 连续 10 秒才提示「单核繁忙」 |
| 高占用进程列表 | ⚠️ | 进程处理器时间差分 ÷ 墙钟 ÷ 逻辑核数，与任务管理器同口径；只显示 ≥1% 的前 6 项。受保护进程读不到处理器时间，计入「读不到」而不是 0% |
| 进程列表可用性 | ✅ | 进程占用需要两次采样，首帧显示「采样中（进程占用需要两次采样才能算出）」；列表为空时状态行说明原因（无 ≥1% 进程 / 读不到几个） |
| 采样状态与完整性 | ✅ | 显示有效帧数、缺失帧数（按未知处理）、间断处数；「持续」判定遇缺帧或间隔 >2.5 秒即断链 |
| 采样生命周期 | ✅ | 页面不可见 / 最小化 / 收进托盘即停采；离开 CPU 页清空历史与差分基准，回来重新累计（不把新旧数据拼成一段「连续 30 秒」） |
| 建议文案 | ✅ | 按档位给可执行建议；瞬时高但连续链被打断时**明确说明为什么不给结论** |

> 诊断规则是 Core 里的纯逻辑类 `CpuLoadAnalyzer`，阈值常量与界面同源；
> 规则覆盖持续判定、间断、缺帧、单核、未知数据等 30 余条用例。
> **不做温度与功耗**：无法可靠获取，见 [已知限制](04-已知限制.md) 第十三节。

### 2.2 CPU 快速优化

流程：**轻量检测 → 展示依据与建议 → 用户勾选确认 → 执行 → 回读验证 → 展示实际结果**。
没有任何「扫描中」的假动画，也不做未经确认的改动。

| 功能 | 状态 | 说明 |
|---|---|---|
| 轻量检测 | ✅ | 用当前诊断结论 + 最近一次进程排名生成候选，每条都带**实测依据、影响范围、回滚方式** |
| 只列能安全结束的项 | ✅ | 系统进程、安全软件、游戏本体、本程序自身、读不到 exe 路径的进程**一律不提供操作**，并在附注里写明被排除的原因 |
| 候选上限 | ✅ | 占用 ≥3% 才算候选，最多 3 项，默认**全部不勾选** |
| 执行闸门 | ✅ | 未勾选任何项时执行按钮不可用；执行器内部再按保护名单过滤一遍（纵深防御） |
| 执行与回读 | ✅ | 结束后观察 5 秒，用同口径（总 CPU、5 秒平均）对比执行前窗口；帧数不足时明确写「无法对比」 |
| 可回滚 | ✅ | 「恢复被结束的进程」按记录的原始路径重新拉起；失败的项逐条报出来。只保证重新启动，不保证恢复窗口与未保存内容 |
| 结果如实上报 | ✅ | 结束 0 个就写「没有进程被结束，系统状态未改变」，并说明跳过 / 拒绝访问各几项 |
| 明确不做 | ✅ | 不改进程优先级、CPU 亲和性、睿频与频率；不承诺帧率提升；不因「CPU 高」就认定是垃圾进程 |

> 复用现有保护逻辑：`EndProcessAction`（内含 `EssentialProcessGuard` 与
> `BackgroundProcessWhitelist`）。**不借道 `GameModeController`**——它会写游戏模式专用的
> 崩溃兜底快照，快速优化覆盖那份快照会导致下次启动弹出错误的还原提示。

| **旧配置迁移**（v2.4.x） | ✅ | v1 `{"processes":[...]}` 与 v2 `endTargets` 都已被默认行为覆盖，迁移时丢弃并提示；保护名单一字不差保留，绝不把旧清单倒成保护 |
| 保护状态持久化 | ✅ | `%LocalAppData%\GameOptimizer\background-whitelist.json`（schemaVersion 3，只存 `protected`）；改一次存一次，失败红字提示 |
| **释放闲置内存** | ✅ | v2.0.0 起作为**可选动作**加入：失败不拦路，但会进 `Warnings` 如实上报 |
| 关闭时自动恢复进程 | ✅ | 退出游戏模式按原路径重新拉起被结束的进程（v1.0.1）；恢复失败如实上报 |
| 必要进程自动保护 | ✅ | Session 0 服务、已注册服务、Windows 组件一律不结束（由 `EssentialProcessGuard` 独立拦截）；这类进程自 v2.4.x 起**不再出现在浮窗列表里** |
| 结束结果如实上报 | ✅ | 明确告知结束几个、释放多少 MB、哪些被系统保护 |
| 失败自动回滚 | ✅ | 任一**必需**动作失败，立即回滚已执行部分 |
| 回滚失败上报 | ✅ | 明确告知哪项没还原，绝不静默显示「已还原」 |
| **可选动作语义** | ✅ | `AddOptional()`：可选动作失败不回滚、不中断，但必须进 `Warnings` |

> 显卡性能偏好已移除：核显机器上没有可调度的独立 GPU，写 `GpuPreference` 不会生效，属于空转项。

> 内存清理的 `Revert()` 是空操作：释放工作集不是状态改动，放出去的页会随进程继续运行自然回到内存，
> 没有「恢复」这回事。它也因此在崩溃兜底快照里不占字段。

## 五、下载页（v2.2.0）

侧边栏「下载」导航项，排在「设置」**上方**。下载内核 `Core/Download/DownloadService`
不依赖任何 WPF 类型，可脱离界面单测。

| 功能 | 状态 | 说明 |
|---|---|---|
| 手动新建任务 | ✅ | 粘贴 http / https 直链，自动识别文件名（可手改），「浏览」选保存目录 |
| 多线程分片 | ✅ | 默认 4 片，1~16 可调；按 4KB 对齐，末片吃掉余数；小于 256KB 不分片 |
| 断点续传 | ✅ | 每片已收字节与片 SHA1 落盘；重启后只对「上次被硬中断」的任务自动续传，用户主动暂停的保持暂停 |
| SHA1 校验 | ✅ | 服务端给 Digest 就比对；没给就如实写「未校验（服务端未提供校验值）」，**不假装通过** |
| 校验失败重下 | ✅ | 用片哈希定位坏片、只重下坏片；定位不到（传输途中混入坏数据）才整份重下，最多 `IntegrityRetries` 轮 |
| 异常重试 | ✅ | 网络类错误指数退避（1× / 2× / 4× 基准，上限 30 秒，带 ±20% 抖动），默认重试 3 次 |
| 实时速度 / 剩余时间 | ✅ | 每秒采样、指数平滑；速度未知时显示「剩余 --」，不编造数字 |
| 全局限速 | ✅ | 令牌桶由所有任务共享，支持「10MB」「500KB」写法，改完立即生效 |
| 任务队列 | ✅ | 最大同时下载数可配（默认 2 个任务 × 每任务 4 片）；名额满时停在「排队中」 |
| 六种状态 | ✅ | 排队中 / 下载中 / 已暂停 / 已完成 / 下载失败 / 已取消；界面按「正在下载 / 下载失败 / 已完成」分组 |
| 批量操作 | ✅ | 全部暂停、全部开始、清空已完成（只删记录，不动已下好的文件） |
| 持久化 | ✅ | 写 `%LocalAppData%\GameOptimizer\downloads.json`，先写 `.tmp` 再原子改名；每 5 秒兜底保存 + 退出前落盘 |
| 打开所在文件夹 | ✅ | 文件在就选中它，不在就打开所在目录，都不在如实说明 |

> 交互与能力参考 PCL（Plain Craft Launcher，作者 龙腾猫跃，https://github.com/Meloong-Git/PCL）
