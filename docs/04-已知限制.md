# 已知限制（v2.2.2）

这一节记录**明确做不到的事**。写出来是为了避免下一版误判现状，也避免把限制当成 bug 去修。

## 一、只有 VXE/ATK（Compx）与蓝牙外设能读电量

**现象**：外设页里部分接收器式无线鼠标仍显示「电量未知」。

**原因**：Windows 只为蓝牙外设提供统一的电量上报（`DEVPKEY_Bluetooth_Battery`，
对应 GUID `{2BD67D8B-8BEB-48D5-87E0-6CDA3428040A}` pid 4）。

**v1.1.0 起**：VXE/ATK（Compx 方案）鼠标通过逆向 hub.atk.pro 驱动得到的私有协议
实时读电量（`VxeBatterySource`，FF02 集合，本机实测 65%）。
罗技 HID++、其他国产厂商的接收器协议仍是私有协议，Windows 不解析——显示「未知」。

**因此**：

- 蓝牙耳机、蓝牙键鼠：能读到百分比 ✅
- **VXE/ATK（Compx）鼠标：能实时读到百分比 ✅（v1.1.0）**
- 其他厂商接收器式无线键鼠：读不到，显示「未知」⚠️
- 有线设备：不需要电量，显示「有线」✅

**不要**为了「有数字可显示」去编造电量或写入猜测值。
> **多台同 VID 设备（v2.1.3）**：一台机器上可能同时枚举到多台 Compx 设备
> （真鼠标 + 已拔出的残留枚举项）。读取时必须**逐个候选接口试**，
> 第一个打不开不代表读不到——只问第一台会让原本能读的电量退化成「未知」。

## 二、「有线 / 无线」在接收器场景是推断，不是读数

Windows 不区分「USB 有线」和「USB 接收器无线」。判定顺序：

1. 读到电量 → 无线（有电池才谈得上电量）
2. 设备名含 `Dongle` / `Receiver` / `接收器` / `Wireless` / `2.4G` → 无线
3. 蓝牙枚举（`BTHENUM` / `BTHLE`）→ 无线
4. USB / HID / ACPI / 板载音频 → 有线

**漏判场景**：一只接收器无线鼠标，产品名里既没有 Dongle 也没有 Wireless
（例如只报 `USB Optical Mouse`），且读不到电量 —— 会被显示成「有线」。
这是信息本身的缺失，不是判定逻辑的 bug。

## 三、耳机只从音频端点识别

HID 消费类集合（音量键、播放键）**不能**当作耳机：
键盘上的媒体键带同样的用途页 0x0C，实测会把罗技 G610 误判成一台耳机。

后果：没有音频端点的「耳机」（例如只用于手机、从未在 PC 上配对过的蓝牙耳机）
不会出现在外设页；纯 USB DAC 但名称不含「耳机 / Headphone」的端点同样不会。

**多只耳机同时连接**（v2.2.2）：每只耳机各自一张卡片，3.5mm 有线耳机与蓝牙耳机可以同时显示。
不会重复计数，靠三条规则：

1. **录音端点直接排除**：MMDevice 端点 ID 前缀 `{0.0.1.00000000}` 是录音、
   `{0.0.0.00000000}` 是播放。本机的「圆孔耳机 (Audio Device)」播放与录音端点**同名且容器不同**，
   只看名字分不出来，只能认这个前缀。名字带「麦克风 / Microphone」的同样排除。
2. **容器 ID 相同 → 同一台**：蓝牙耳机的 A2DP 播放端点与 HFP 免手持端点按容器合并。
3. **容器读不到时退化判重**：连接方式一致，且型号相同或互为前缀
   （`DM02` 与 `DM02 Hands-Free AG Audio`）。

## 四、外设页不区分「当前插着」和「曾经配对过」

扫描基于设备树的**当前存在**设备。耳机拔出后端点会消失，下次刷新就不显示。
未做「历史设备记忆」——那需要额外的持久化与过期策略，本版不做。

## 四·一、进程恢复的前提（v1.0.1）

关闭游戏模式时，只有**结束前能读到可执行文件路径**的进程才会被自动恢复；
读不到路径的进程（反作弊保护、权限不足）不自动恢复，界面如实说明。
恢复是「重新拉起同名程序」，不恢复窗口位置、未保存内容等运行时状态。

## 五、游戏显存需求表是估值

「显存充足 / 紧张」按每款游戏自己的正常需求判定，需求来自内置需求表（`GameVramDemand`）。

- **已收录的游戏**：表里给了 1080p 四档画质的量级，取偏保守的上沿
- **未收录的游戏**：按安装体积推断，界面会标注「估算值」，不要当成实测

需求表只收录经过确认的条目。**猜出来的数字比不显示更糟**。

判定固定使用「1080p 高画质」这个正常配置，不随用户实际画质变化。
若用户在游戏内开了 4K 极致，实际需求会高于界面显示值。

底线：`TightRatio = 0.85`，即需求超过**当前剩余显存**的 85% 判「紧张」，留 15% 余量给游戏运行中的显存增长。

## 六、帧时间采集与卡顿归因已移除

v1.0.0 按用户要求把「数据」页删掉，改为「外设」页。随之移除：

- `FrameTimeSource`（PresentMon 调用）
- `FrameTimeAnalyzer`、`DiagnosisEngine`、`DiagnosisFinding`
- `ChartGeometry`、`Sparkline`（自绘曲线）
- `SampleFrame.FrameTimeMs` 字段

外部脚本 `tools/verify-frametime.ps1` 保留，用于单独验证 PresentMon 的 ETW 链路，
不再被程序调用。

**这意味着工具不再回答「卡顿到底来自哪里」**，只回答「现在占用多少、外设还剩多少电」。
加回去需要重新引入上述模块，并处理 ETW 权限问题（见下一节）。

## 七、PresentMon 的 ETW 权限问题（保留备查）

若要恢复帧时间采集：

- 启动 ETW 追踪会话需要管理员，或账号属于 `Performance Log Users` 组
- 组权限配好也可能因为父进程是低完整性而失败（实测 `0xC0000022`）
- `--output_file` 写出的 CSV 在采集期间**独占打开**，外部读不到，必须用 `--output_stdout`

## 八、平台支持有限

只支持 Steam 与 WeGame。Epic、Xbox、Ubisoft Connect、独立安装的游戏都不会出现在列表里。

## 九、反作弊游戏的进程路径读不到

三角洲行动的 ACE、无畏契约的 Vanguard 会阻止跨进程读取 `MainModule` / WMI `ExecutablePath`。

**已应对**：`GameProcessDetector` 有「进程名前缀匹配」退化路径，不依赖读路径。
**遗留**：若游戏进程名与扫描到的 exe 主名毫无相似性，仍会漏检。

## 十、界面层的技术债

- `MainViewModel` 里直接用 `System.Windows` 类型的地方已清理（改为纯数据 + XAML 触发器）
- 没有历史数据持久化，关掉程序数据就没了
- 无边框窗口在**非 DPI 缩放 100%** 的屏幕上圆角与描边会有轻微模糊（`WindowChrome` 的固有行为）

## 十一、托盘行为说明（v1.0.2）

- **点窗口关闭按钮 = 收进托盘**，进程继续后台采集；只有托盘右键「退出」才真正结束。
  要彻底关闭程序，请从托盘图标退出——这是最初「托盘常驻」要求的既定行为，不是 bug。
- 托盘图标为运行时自绘（exe 未嵌入 .ico 资源），风格与窗口主题一致。

## 十二、内存优化做不到的事（v2.0.0）

### 提权也清不掉的进程

释放工作集需要对目标进程持有 `PROCESS_SET_QUOTA`。以下情况即使管理员也无效：

- **受保护进程**（PPL，如杀毒引擎的核心服务）——`OpenProcess` 直接拒绝
- **反作弊进程**（ACE / Vanguard）——同样拒绝跨进程操作
- **其他账户的会话**

这些会如实记为「拒绝访问」并出现在结果里，**不会假装清过**。
界面会区分「没提权」（提示去提权）与「已提权仍被拒」（说明受系统保护）。

### 释放量以系统可用内存为准，会比"看起来"小

实测同一轮清理：逐进程工作集减少合计 **2.9 GB**，系统可用内存只涨了 **461 MB**。

原因是共享页面（同一份 DLL / .NET 运行时）被多个进程同时映射，算进每个进程的减少量里。
拿 2.9 GB 去展示等于虚假宣传，所以界面上的数字取系统可用内存实测差。

**这意味着可能看到「已回收闲置页面，但系统可用内存未明显变化」**——
页面只是从工作集挪到了备用列表，并没有真正变成"可用"。这是如实呈现，不是功能失效。

### 只做逐进程路径，不做全局清理

PCL2 的 `NtSetSystemInformation(SystemMemoryListInformation)` 全局路径需要
`SeProfileSingleProcessPrivilege`（管理员），能额外清理已修改页与备用列表。
本版**只用逐进程路径**：普通权限下即可覆盖本账户进程，覆盖面更实用。
全局清理留作 v2.1 扩展点。

### 效果是时点的，会自然回落

内存占用会随使用继续上涨——这是操作系统的正常行为，不是优化失效。
本工具不提供「自动定时清理」：频繁清工作集只会让进程反复缺页，反而更卡。

## 十三、温度监控：明确不做（v2.0.0 评估结论）

规划文档 v2.2.0 要求「CPU/GPU 温度监控，撞温度墙预警」。**评估后决定不做**，理由如下。

### 实测：ACPI 路径给的不是芯片温度

| 路径 | 结果 |
|---|---|
| `MSAcpi_ThermalZoneTemperature`（WMI） | **拒绝访问** |
| `\Thermal Zone Information(*)\Temperature`（PDH） | 27.9°C，**连采 5 次一个数字都不动** |
| 同上，CPU 压到 79% 时 | **仍是 27.9°C** |
| `\Thermal Zone Information(*)\High Precision Temperature` | 3010（=27.95°C），同样恒定 |
| `Throttle Reasons` | 0（只表示「没在降频」，不是温度） |

这个 27.9°C 是 **ACPI 热区的环境温度**，不是芯片结温，**完全不随负载变化**。
把它当「CPU 温度」显示就是编造一个看起来很专业的假数字——正是本项目
「不可观测的不报结论」原则要避免的。

GPU 侧更彻底：`Get-Counter -ListSet` 里与 GPU 相关的只有
`GPU Engine` / `GPU Adapter Memory` / `GPU Local·Non Local Adapter Memory` /
`GPU Process Memory`，**没有任何温度计数器**。

### 要真实温度只有一条路，但代价不可接受

读 **MSR `0x1A2`（IA32_PACKAGE_THERM_STATUS）** 或 **EC / SuperIO**，
必须内核态驱动（LibreHardwareMonitor / WinRing0 一类）。

这与项目既定原则冲突：**不装驱动、不做静默安装、不改系统服务**。
且多数反作弊会拦截这类驱动加载，装上反而可能让游戏启动失败。

**结论**：不引入。若将来用户明确要求并接受驱动风险，再单独立项评估。

## 十四、被筛掉的系统压力指标（v2.0.0 实测）

为回答「卡顿发生在哪一环」，评估过五项候选指标，**只保留两项**。
其余三项的筛除理由都是实测得出的，避免以后重复试错。

### 保留：总 CPU、磁盘吞吐

| 指标 | 实测 | 保留理由 |
|---|---|---|
| 总 CPU | 空闲 1.4% → 满载 74~79% | 现有界面只有「单核峰值」，看不出整机是否被吃满 |
| 磁盘吞吐 | 空闲 0.16 MB/s → 写入时 **10.95 MB/s**（差 68 倍） | 回答「贴图流式加载卡不卡在磁盘」，信号清晰 |

### 筛除：处理器队列长度

`\System\Processor Queue Length` 只统计就绪队列里等 CPU 的线程。

| 场景 | 队列 | 总 CPU |
|---|---|---|
| 空闲 | 0 | 1.4% |
| 32 个后台 Job | **0** | 29% |
| 20 个独立进程压满 | **0~2** | 74~79% |

24 核机器上跑 20 个满负荷进程，队列仍只有 0~2。它只在「少数几个核被抢占」时
才有信号，绝大多数时候是 0，**误读风险远大于价值**。

### 筛除：分页文件使用率

`\Paging File(_Total)\% Usage` 实测 25%，但**同期 `\Memory\Pages/sec` 为 0**
——说明系统完全没在换页，那个 25% 是历史占用。

单看它会把「毫无压力」读成「内存吃紧」。要它有意义必须配 `Pages/sec` 一起看，
而真要看换页，直接看 `Pages/sec` 就够了，不必绕道分页文件。

### 筛除：网络吞吐

能采到（实测一次 HTTP 请求 18 KB/s，且必须用 `PerformanceCounter` 直接指定实例名——
`Get-Counter` 通配符查询在本机读不出数）。但在线游戏的卡顿来自**延迟**，不是吞吐，
看吞吐回答不了「为什么延迟高」。

## 十五、系统压力面板的采集前提

两项指标都走 PDH 计数器，**不需要管理员权限**。若某个计数器在本机不存在，
另一项照常工作（每项独立降级），采不到的项目会在面板副标题里列出，不显示 0 冒充读数。

## 十六、CPU 峰值为什么取「P 核峰值」而不是全局峰值（v2.0.2）

本机是 i7-1360P：**4 大核（P-core）8 线程 + 8 小核（E-core）**。
界面上的 CPU 仪表取**性能核（P 核）中最高的一个**，不取全部 16 线程的最高值。

### 实测：全局峰值会误报

用进程亲和性把 8 个满载进程分别绑到不同核上：

| 负载位置 | 全局单核峰值 | **P 核峰值** | E 核峰值 |
|---|---|---|---|
| 空闲 | 30.5% | 30.5% | 16.6% |
| **8 进程绑 E 核满载** | **100%（红色报警）** | **24.9%（绿色）** | 100% |
| 8 进程绑 P 核满载 | 93.7% | 93.7% | 14.1% |
| 单线程游戏负载 | 94.4% | 94.4% | 27.2% |

第二行就是要避免的误判：后台进程挤满小核时，全局峰值亮红 100%，
而真正跑游戏的 P 核只有 24.9%——玩家会白白去降画质。

### 为什么 P 核才是游戏的主战场

实测单线程满载时，操作系统把线程调度到**逻辑核 2（P 核）94.4%**，同刻 E 核峰值仅 27.2%。
游戏主线程吃的是单核性能，落点就是 P 核；E 核主要承接后台。

### 全同构机器上行为不变

没有大小核的机器（所有逻辑处理器效率等级相同）上，P 核峰值 == 全局峰值，
仪表标题也保持「CPU 单核峰值」。区分靠 `GetSystemCpuSetInformation` 的 `EfficiencyClass`。

### 踩过的坑：空缓冲探测调用必然返回 false

`GetSystemCpuSetInformation` 第一次用空缓冲探测长度时**返回 false**
（`ERROR_INSUFFICIENT_BUFFER`）。旧实现拿返回值当失败判据，直接返回空列表，
于是本机被误判成「16 线程同构」，整个大小核区分功能**静默失效**。
现在只检查它有没有吐出长度，不看返回值。
回归用例：`混合架构机器上检测不得退化成都算性能核`。

## 十七、游戏内悬浮窗：评估后不做（v2.2.0 评估结论）

规划文档 v2.2.0 要求「游戏内悬浮窗（Overlay）」。**实现后评估认为价值不足，已撤回**，
理由记录如下，避免以后重复评估。

### 为什么它被做出来又被撤掉

用户的硬约束是「**保证账号安全，不要被反作弊系统检测为异常**」。
这条约束与悬浮窗的核心价值直接冲突：

| 悬浮窗的价值 | 前提 | 与约束的关系 |
|---|---|---|
| 游戏中随手看到占用 | 能覆盖游戏画面 | 独占全屏必须注入 DLL + Hook D3D → **必然被封** |
| 回答「我是不是掉帧了」 | **需要帧率** | 帧率必须 PresentMon 定向监控游戏进程 → 反作弊敏感点 |

被约束砍掉上面两条后，只剩下「窗口化游戏下也能看占用」这一条。
而窗口化游戏下 Alt-Tab 切到主界面只要一秒，主界面的数字更大更清楚——
**这个残余价值不成立**。

### 如果将来要重新做，需要先决定的事

1. **要不要帧率**：不要帧率就没有做悬浮窗的必要，主界面已经覆盖
2. **能不能进独占全屏**：能进就必须注入，与「不注入游戏进程」原则冲突
3. 若要放开注入，必须由用户明确接受封号风险，并写进知情同意

### 评估时实测到的数据（仍有参考价值）

PresentMon 2.6.0 的开销**完全可忽略**，问题从来不是性能：

| 项 | 实测 |
|---|---|
| 15 秒采集累计 CPU | 31 ms（≈0.12% 单核） |
| 峰值内存 | 13.2 MB |
| 提权要求 | ETW 会话需管理员 |
| 副作用 | 异常退出会残留 ETW 会话，需 `logman stop PresentMon -ets` 清理 |

若将来某个功能（如「优化前后对比」）需要帧率，这些数据可以直接复用。

## 十八、下载器的能力边界（v2.2.0）

### 必须返回 Content-Length 才能下

探测拿不到文件长度（chunked 编码、直播流）时任务**直接失败**，
而不是显示一个永远 0% 的假进度。没有总长就无法分片、无法断点续传、也无法算百分比。

### 分片与续传依赖服务端支持 Range

- 服务端明确忽略 Range（发 Range 却回 200）：整任务退回单线程从零下载，并提示用户；
- 断点位置超出文件长度（服务端文件已更新）：提示「请点重新下载」，不静默对齐；
- 只支持 `http` / `https` 绝对地址，不猜协议（避免把填错的链接下成奇怪的东西）。

### SHA1 校验只对「服务端给了 Digest」的文件成立

服务端没给校验值时，卡片上如实写 **「未校验（服务端未提供校验值），本地 SHA1：xxxx」**。
有期望值才谈得上通过 / 不通过。

### 校验失败不一定能定位到具体分片

- **能定位**：写完之后被改坏（磁盘静默错误、被外部程序改写、断点与字节不符）——
  逐片重算 SHA1 与落盘时记下的片哈希比对，只重下对不上的片；
- **定位不到**：坏字节是传输途中混进来的——片哈希算的正是这些坏字节本身，
  本地没有任何对照基准，只能整份重下；
- 单分片任务不做定位（重下一片与整份重下是同一件事）。

### 其它

- **不做** BT / 磁力 / 网盘直链解析，也不做镜像加速（对任意直链没有意义，PCL2 的镜像是为 MC 资源站做的）；
- 暂停后再继续依赖服务端的 Range；服务端在暂停期间换了文件，只能靠校验兜住；
- 已完成任务的记录可以清空，但**已下好的文件不动**——清空只清列表；
- 「取消」会删掉临时分片文件，「暂停」保留（这是两者的区别）。
