# 已知限制（v0.5.0）

这一节记录**明确做不到的事**。写出来是为了避免下一版误判现状，也避免把限制当成 bug 去修。

## 一、帧时间采集需要特权

**现象**：点「开始采集帧数据」后提示 `access denied`。

**原因**：PresentMon 启动 ETW 追踪会话需要以下任一条件：
- 以管理员身份运行
- 账号属于 `Performance Log Users` 组，**且**启动进程的父进程不是低完整性进程

**已验证的事实**：
- 管理员 PowerShell 下 PresentMon 输出 `Started recording.` / `Stopped recording.`，正常工作
- 组权限配置正确（SID `S-1-5-32-559` 在令牌中且状态为 `Enabled group`）
- 但从低完整性会话启动时仍失败，错误 `0xC0000022`

**未解决**：
- 程序自身未实现自动提权（会弹 UAC）
- 普通用户桌面启动是否可用，**尚未验证**（测试者一直从受限会话启动）

**不要尝试**：修改 ACL、伪造令牌、绕过 UAC——都超出范围。

## 二、PresentMon 的 CSV 无法轮询

`--output_file` 写出的 CSV 在采集期间是**独占打开**的，外部连 `FileShare.ReadWrite` 都读不到：

```
The process cannot access the file because it is being used by another process.
```

**因此必须用 `--output_stdout` 流式读取**。这条已经写进实现，不要改回文件轮询。

## 三、游戏显存需求表是估值

首页的「显存充足 / 紧张」按每款游戏自己的正常需求判定，需求来自内置需求表（`GameVramDemand`）。

- **已收录的游戏**：表里给了 1080p 四档画质的量级，取偏保守的上沿
- **未收录的游戏**：按安装体积推断，界面会标注「估算值」，不要当成实测

需求表只收录经过确认的条目。**猜出来的数字比不显示更糟**，所以未收录的一律走体积推断并标明来源。

判定固定使用「1080p 高画质」这个正常配置，不随用户实际画质变化。
若用户在游戏内开了 4K 极致，实际需求会高于首页显示值。

底线：`TightRatio = 0.85`，即需求超过本机显存的 85% 判「紧张」，留 15% 给桌面与系统。

## 四、游戏状态与实测采集分离

首页的结论来自需求表与本机显存，**不需要先跑一局采集**。
数据页的会话实测（`VramAssessor`）是另一条链路，二者互不覆盖。

## 五、平台支持有限

只支持 Steam 与 WeGame。Epic、Xbox、Ubisoft Connect、独立安装的游戏都不会出现在列表里。

## 六、网络问题完全没覆盖

用户最初描述的「网络波动大」不在 v0.5.0 范围内。当前的所有指标都是本机性能，**无法区分「渲染卡」和「网络卡」**。

诊断引擎里「帧时间平稳」的结论会提示「若仍有卡顿感，更可能来自网络或输入延迟」，但这只是提示，没有数据支撑。

## 七、反作弊游戏的进程路径读不到

三角洲行动的 ACE、无畏契约的 Vanguard 会阻止跨进程读取 `MainModule` / WMI `ExecutablePath`。

**已应对**：`GameProcessDetector` 有「进程名前缀匹配」退化路径，不依赖读路径。
**遗留**：若游戏进程名与扫描到的 exe 主名毫无相似性，仍会漏检。

## 八、UI 层的技术债

- `MainViewModel` 里直接用了 `System.Windows.Visibility`，把 WPF 类型泄漏进了 ViewModel
- 曲线只保留最近 120 点（约 2 分钟），更长的会话会被截断
- 没有历史数据持久化，关掉程序数据就没了

## 九、工作区里一个删不掉的空目录

`src/GameOptimizer.App/bin/` 下有个空目录被残留进程占用，无法删除。它已在 `.gitignore` 中，**不影响仓库和交付**，下次 `dotnet clean` 或重启后自然消失。
